# Как устроен сайт — то, что нужно маркетинговому агенту

Снято 2026-08-20 инвентаризацией (`00_bootstrap.md`, шаг 1).
Подробности разработки — в корневом `README.md`, здесь только то, что влияет
на маркетинг.

## Стек

| Слой | Что |
|---|---|
| Фреймворк | Next.js 14.2.35, App Router, TypeScript |
| Рендер | статика (SSG) для публичных страниц, серверные компоненты |
| Стили | готовый `public/assets/site.css`, без Tailwind |
| Процесс | `next start -p 3005` под systemd, юнит `corebridge-site.service` |
| Отдача наружу | nginx на хосте, `/etc/nginx/sites-available/corebridge.ru.conf` |
| Исходники | `/opt/corebridge-site` — этот репозиторий, ветка `main` |

## Куда что ведёт

```
corebridge.ru/        → Next.js 3005      ← наша территория
corebridge.ru/lk/*    → lk-api 3000       ← бэкенд, не трогаем
corebridge.ru/api/v1/*→ bridge 3001 и license-service 3002
admin.corebridge.ru   → админка
```

⚠️ **Бэкенд правится только промтом.** `/opt/corebridge` выкатывается автодеплоем
с локального ПК Дмитрия, ручные правки затираются. Всё, что требует изменений
на сервере (например, сохранять utm при регистрации), оформляется как промт
в `Documents/prompts/`, а не делается руками.

## Где происходят ключевые действия

Ни одно из них не происходит в этом репозитории — форма шлёт запрос в API,
а результат оседает в БД. Поэтому события регистрации и оплаты берутся
не из трекера, а прямо из таблиц.

| Действие | Где на сайте | Куда уходит | Где оседает |
|---|---|---|---|
| Заявка с формы | `app/(site)/(public)/contacts/ContactsBody.tsx` | `POST /lk/public/contact` | `platform.contact_requests` |
| Регистрация | `app/(site)/(auth)/register/` | `POST /lk/auth/register` | `platform.users`, `platform.tenants` |
| Вход | `app/(site)/(auth)/login/LoginForm.tsx` | `POST /lk/auth/login` | `platform.refresh_tokens` |
| Оплата | `app/(site)/(lk)/billing/pay/` | `POST /lk/billing/pay` → Robokassa | `platform.payments` |

## Аналитика

**Внешних счётчиков нет и не планируется.** Яндекс.Метрика и GA не подключены;
CSP в nginx (`script-src 'self'`) не пускает сторонние скрипты, и счётчик молча
не работал бы — ровно так, как это уже случилось со шрифтами Google.

Что есть вместо:

1. **Логи nginx** — `/var/log/nginx/access.log*`, формат `combined`, ротация 14 суток.
   Разбирает `scripts/ingest_nginx.py`.
   ⚠️ В формате нет `$host`: все vhost'ы пишут в один файл, и отделить
   `corebridge.ru` от `admin.corebridge.ru` можно только по пути запроса.
2. **Свой счётчик** — `public/assets/mkt.js` → `app/m/e/route.ts` → JSONL
   в `marketing/data/tracker/`. Даёт то, чего нет в логах: повторные визиты,
   источник первого касания, нажатия на размеченные `data-mkt` элементы.
3. **Продуктовая БД** — `platform.*` в контейнере `corebridge-postgres`,
   только SELECT через `scripts/query_events.py --pg`.
4. **Яндекс.Вебмастер** — `scripts/fetch_webmaster.py`, единственная внешняя
   зависимость. Без него не видно поисковых запросов и позиций.

## Что можно и чего нельзя менять

Можно, но только в ветку `claude/*` и не более 3 страниц за прогон:
`title`/`description` страниц кроме защищённых, тексты разделов,
микроразметку, внутренние ссылки, содержимое `content/docs/epf/*.html`.

Нельзя без человека: `robots.ts`, `sitemap.ts`, структуру URL, цены,
юридические тексты (`content/legal/`), формы оплаты, CSP и vhost.

## Где место новым текстам

Раздела «блог» на сайте **нет**. Есть документация: `content/docs/epf/*.html`
плюс `manifest.json` с разделами — 30 страниц, каждая под свой запрос
(«подключить озон 1с», «маркировка честный знак», «остатки»). Новый текст
почти всегда должен становиться доработкой существующей страницы отсюда,
а не новой сущностью. Отдельный `/blog` — это работа кодом в основном
репозитории, и заводить его имеет смысл, только когда доки исчерпаны.
