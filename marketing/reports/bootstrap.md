## Что сделано

### Сбор данных (работает уже сейчас)

| Скрипт | Что делает |
|---|---|
| `ingest_nginx.py` | логи → `data/events.db`, отделяет людей от роботов |
| `ingest_tracker.py` | JSONL своего счётчика → та же база |
| `daily_export.py` | суточный срез → `data/YYYY-MM-DD.json` |
| `fetch_webmaster.py` | запросы и позиции Яндекса → `data/search/` |
| `query_events.py` | единственный способ читать данные; писать нельзя |
| `watchdog.py` | каждые 15 минут: сайт, 5xx, битые ссылки, сертификат, лиды |
| `digest.py` | утренняя сводка цифрами в Telegram |
| `notify_telegram.py` | отправка отчётов и черновиков |
| `run.sh` | обёртка для cron: сбор отдельно, прогон агента отдельно |

**Ключевое решение архитектуры:** сбор данных и сигналы не зависят от языковой
модели. Прогон агента может упасть, упереться в лимит или отработать плохо —
цифры всё равно соберутся, а сообщение о новой заявке всё равно придёт.
Модель отвечает за смысл, но не за то, дойдут ли данные.

### Хранилище

`data/events.db`, SQLite, схема — `scripts/schema.sql`.

Отступление от `00_bootstrap.md`, где предполагалась таблица `mkt_events`
в БД сайта, и объяснение почему:

- своей БД у сайта нет, а продуктовый Postgres принадлежит бэкенду, который
  выкатывается автодеплоем с чужого ПК — наша таблица там повод для конфликта;
- регистрации, заявки и оплаты **уже** лежат в `platform.*`; копировать их
  в события значит завести второй источник правды;
- серверный трекинг «в местах кода, где происходит signup» из шага 3 промта
  здесь невозможен: этих мест в репозитории сайта нет, они в `lk-api`.

Персональных данных в базе нет. IP хранится хешем с постоянной солью —
достаточно, чтобы отличать посетителей, недостаточно, чтобы установить лицо.

## Что должен сделать человек

### 1. Написать боту (1 минута) — без этого не работает ничего

Бот `@CoreBridge_ru_bot` жив, токен принят, но отправка отвечает
`chat not found`: **Telegram не даёт боту написать первым**. Открой бота,
нажми «Начать», потом:

```bash
cd /opt/corebridge-site/marketing/scripts
./tg_chat_id.py --test
```

Скрипт покажет настоящий `chat_id` и отправит проверочное сообщение.
Если id отличается от `654445624` — поправить `TG_CHAT_ID` в `marketing/.env`.

### 2. Поставить cron (1 минута)

```bash
crontab /opt/corebridge-site/marketing/scripts/crontab.txt
crontab -l
```

Часы сервера — UTC, в файле уже пересчитано на московское время.
Прогоны агента пропускаются молча, пока не сделан шаг 4.

### 3. Яндекс.Вебмастер (15 минут) — самое важное

1. `webmaster.yandex.ru` → добавить `corebridge.ru`
2. Подтвердить права. **Мета-тег не подойдёт** — он ставится в `<head>`
   главной, а это защищённая страница. Проще файлом: Вебмастер даст
   `yandex_XXXX.html`, положить его в `public/`, и он отдастся с корня.
   Скажи мне имя файла — положу и подготовлю правку.
3. Отправить `https://corebridge.ru/sitemap.xml`
4. Токен для API: `oauth.yandex.ru` → создать приложение,
   права «Яндекс.Вебмастер: получение информации», выпустить токен
5. Записать в `marketing/.env`:
   ```
   YA_WEBMASTER_TOKEN=...
   ```
   затем `./fetch_webmaster.py --setup` покажет `USER_ID` и `HOST_ID` —
   их тоже в `.env`.

### 4. Установить claude CLI, если нужны прогоны агента по расписанию

На сервере его нет — я подключён к нему извне. Сбор и сигналы работают без него,
но ежедневный разбор, тексты и гипотезы — нет.

```bash
npm i -g @anthropic-ai/claude-code
claude   # один раз войти
```

После этого строки `run.sh agent ...` в cron начнут отрабатывать.
Расход по каждому прогону пишется в `logs/*.json` (`total_cost_usd`).

### 5. Посмотреть и смержить ветку со счётчиком

```bash
git diff main..claude/marketing-bootstrap -- app/ public/ middleware.ts
```

После мержа — пересобрать и перезапустить сайт (это уже прод):

```bash
npm run build && sudo systemctl restart corebridge-site
curl -s -o /dev/null -w '%{http_code}\n' -X POST https://corebridge.ru/m/e \
     -H 'Content-Type: application/json' -d '{"event":"pageview","url":"/test"}'
# ожидается 204, затем должен появиться marketing/data/tracker/<дата>.jsonl
```

### 6. Необязательное, но сильно улучшит данные: отдельный лог сайта

Сейчас все vhost'ы пишут в один `access.log` форматом `combined`, где нет
ни `$host`, ни времени ответа. Из-за этого сайт от админки отделяется только
по пути запроса, а скорость страниц не измерить вовсе.

В `nginx.conf` (http-секция):

```nginx
log_format mkt '$remote_addr $host [$time_local] "$request" $status $body_bytes_sent '
               '"$http_referer" "$http_user_agent" rt=$request_time';
```

В vhost `corebridge.ru`:

```nginx
access_log /var/log/nginx/corebridge.ru.access.log mkt;
```

После этого скажи — я научу `ingest_nginx.py` читать новый формат.
Правку vhost не делаю сам: это прод-конфигурация.

   регистрация с подтверждённой почтой? От этого зависит вся воронка в отчётах.
4. **Telegram-канал уже есть?** H-003 предполагает публикацию в свой канал.
   Если канала нет, гипотеза проверяет не тексты, а его отсутствие.

## Чего система не умеет

- Не видит поисковых запросов без Вебмастера (шаг 3 выше)
- Не отличает визит с телефона от визита с компьютера в логах — только
  через свой счётчик, после мержа ветки
- Не знает, чем закончилась заявка: статуса сделки нигде нет
- Не работает с платной рекламой — сознательно вне рамок
- Ничего не публикует сама: все черновики публикует человек
