# Bootstrap: разовая настройка

Запускается ОДИН раз, в интерактивном режиме (не через cron), под наблюдением человека.
Задача — понять сайт и построить систему сбора событий. Ничего не публиковать.

## Шаг 1. Инвентаризация

Изучи исходники сайта (путь указан в CLAUDE.md, раздел 4) и опиши в
`knowledge/stack.md`:

- Стек: язык, фреймворк, шаблонизатор, СУБД, версии
- Как устроен роутинг и где рендерятся страницы (куда вставлять трекер)
- Есть ли уже система аналитики (Метрика, GA, свои логи) — что именно она пишет
- Где в коде происходят ключевые действия: регистрация, вход, оплата,
  отправка формы. Укажи файл и функцию для каждого.
- Список всех публичных страниц с их title/description/H1 — в `knowledge/pages.md`
- Что нельзя трогать → предложи список для `knowledge/protected_pages.md`

## Шаг 2. Схема событий

Спроектируй таблицу событий и запиши DDL в `scripts/schema.sql`.
Минимальный набор полей:

- `ts` — время события
- `visitor_id` — first-party cookie, срок жизни 1 год
- `session_id` — сессия, 30 мин неактивности
- `user_id` — если авторизован, иначе NULL
- `event` — тип: `pageview`, `signup`, `login`, `payment`, `form_submit`, `cta_click`
- `url`, `referrer`
- `utm_source/medium/campaign/content/term`
- `first_touch` — источник первого визита этого visitor_id (для атрибуции)
- `meta` — JSON для деталей события (сумма оплаты, id тарифа, id формы)

Плюс индексы по `ts`, `event`, `visitor_id`.

**Не применяй DDL сам.** Выведи SQL и инструкцию, человек применит вручную.

## Шаг 3. Трекер

Подготовь в ветке `claude/bootstrap-tracking`:

- **Серверная часть** — запись событий `signup`, `login`, `payment`, `form_submit`
  прямо в тех местах кода, которые нашёл на шаге 1. Это точные данные,
  их не блокируют блокировщики. Приоритет — здесь.
- **Клиентская часть** — минимальный JS (< 3 КБ, без внешних зависимостей,
  async) для `pageview` и `cta_click`. Ставит cookie, шлёт POST на свой эндпоинт.
- **Эндпоинт приёма** — с валидацией и rate-limit, чтобы его нельзя было засыпать.
- Отдельный пользователь БД с правами только SELECT на таблицу событий —
  под ним будет работать ежедневный агент.

Требования: не замедлять рендер, не ломать работу сайта при отказе трекера,
не собирать персональные данные (email, телефон, платёжные данные — только id).

## Шаг 4. Скрипты чтения

- `scripts/query_events.py` — обёртка для SELECT-запросов под read-only юзером
- `scripts/daily_export.py` — суточный срез в `data/YYYY-MM-DD.json`:
  визиты, уники, источники, топ страниц входа, воронка visit→signup→payment,
  конверсии, сравнение с прошлой неделей
- `scripts/fetch_webmaster.py` — выгрузка запросов и позиций из Яндекс.Вебмастера

## Шаг 5. Отчёт

`reports/bootstrap.md`: что сделано, что человек должен применить руками
(DDL, токены, мерж ветки), какие вопросы остались, каких данных не хватает
для полноценной работы.

Затем остановись. Не мержи ветку, не применяй миграции.
