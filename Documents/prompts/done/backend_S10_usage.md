# S10 — Учёт операций: лимит в тарифе есть, счётчика нет

**Приоритет:** 🟠 не ломает работу, но делает лимиты декоративными: `monthly_operations`
продаётся в каждом тарифе, а сколько операций израсходовано — не знает ни клиент, ни вы.
**Объём:** новый счётчик по образцу уже работающего `n8n_executions_month` + две правки
в том, как этот образец заполняется.

Основание: вы сами написали об этом в `site_S1_S7_RESPONSE.md` §4.4 — «лимит есть в каталоге
и в JWT, но ни одного инкремента и ни одной проверки в коде нет». Ниже — что нужно сайту,
и заодно две вещи, которые всплыли при прогоне тарифов на проде 2026-07-29.

---

## 1. 🟠 `limit_value` в счётчике не связан с тарифом

`services/bridge/event-dispatcher.js` создаёт строку счётчика лениво, при первом событии,
и берёт лимит так:

```js
async function _getN8nExecLimit(pool, tenantId) {
  // …SELECT limit_value FROM platform.usage_counters WHERE tenant_id = $1 …
  return 1000; // safe default if no row exists yet
}
```

То есть при самом первом запуске в месяце лимит записывается как **1000** — вне
зависимости от тарифа. По каталогу должно быть 500 у «Пробного», 500 у «Старта»,
10 000 у «Бизнеса», 20 000 у «Профессионала». Дальше `ON CONFLICT UPDATE` лимит не трогает,
и неверное число живёт до конца месяца.

**Что сделать.** Брать лимит из каталога тарифов по текущему плану тенанта
(`config/plans.js` → `PLANS[plan].limits.n8n_executions_month`), а `1000` оставить
только на случай неизвестного плана. И при смене тарифа обновлять `limit_value`
в строке текущего периода — иначе человек оплатил «Профессионала», а упирается
в лимит «Пробного» до первого числа.

## 2. 🟠 Пока строки нет, сервер отдаёт «лимит 0»

`GET /lk/dashboard` собирает `n8n_usage` только из `usage_counters`:

```js
let n8nUsage = { used: 0, limit: 0, is_limit_hit: false, period: null };
```

Строка появляется лишь после первого запуска, поэтому свежеоплаченный «Профессионал»
получает `n8n_usage: {used: 0, limit: 0, …}`. Отличить «тариф без n8n» от «ещё не
запускали» по ответу невозможно.

Проверено на проде: тенант переведён на `professional`, `/lk/dashboard` вернул `limit: 0`.
Сайт из-за этого писал оплатившему человеку «на пробном тарифе n8n недоступен» —
я уже исправил, лимит на всех экранах ЛК беру из `GET /lk/plans`. Но правильнее, чтобы
`limit` в `n8n_usage` всегда отражал тариф, а нулём был только `used`.

**Что сделать.** Если строки в `usage_counters` нет — подставлять лимит из каталога
тарифов, а не ноль. Одна строчка в `dashboard.service.js`, поведение при наличии строки
не меняется.

## 3. Собственно счётчик операций

Сейчас в `platform.usage_counters` живёт единственный `counter_type` —
`n8n_executions_month`. Нужен второй, для `monthly_operations`.

**Первое, что нужно решить: что считать операцией.** Из кода это не выводится, а от ответа
зависит и цифра, и место инкремента. Варианты, как я их вижу:

| Вариант | Где инкрементировать | Что получает клиент |
|---|---|---|
| Событие, принятое от 1С | `queue-writer` при записи в `events` | «сколько данных я отправил» |
| Успешно доставленный вызов адаптера | `event-dispatcher` после `markProcessed` | «сколько полезной работы сделано» |
| Любой запрос к API типа 1 | middleware bridge | ближе к нагрузке, но растёт от ретраев |

Мне для интерфейса годится любой — важно, чтобы определение было одно и его можно было
написать человеку словами рядом с прогресс-баром. Склоняюсь ко второму: клиент платит
за доставленную работу, а не за свои ретраи. Решать вам — напишите, что выбрали.

**Что реализовать после решения:**

- инкремент по образцу `usageService.incrementExecution`, `counter_type = 'monthly_operations'`,
  `period = TO_CHAR(NOW(), 'YYYY-MM')`, `limit_value` — из каталога тарифов (см. п. 1);
- отдавать факт в `GET /lk/dashboard` рядом с `n8n_usage`:

```json
"operations_usage": { "used": 1234, "limit": 100000, "is_limit_hit": false, "period": "2026-07" }
```

- включить в уже существующее уведомление `limit_exceeded` пороги 80 % и 100 %
  (канал и матрица уведомлений готовы с пакета S4 — нужен только повод);
- решить, что происходит при 100 %: жёсткий отказ или предупреждение. Сейчас у
  `n8n_executions_month` есть флаг `is_limit_hit`, но ни одна проверка на него не смотрит,
  то есть лимит нигде не применяется. Если применять не планируется — так и скажите,
  я напишу на экране «мягкий лимит», а не буду обещать блокировку.

## Как проверить, что починилось

```bash
# 1. Лимит соответствует тарифу до первого запуска
curl -s -H "Cookie: lk_session=<сессия>" https://corebridge.ru/lk/dashboard | jq '.n8n_usage'
# на «Профессионале» ожидаем limit: 20000, а не 0

# 2. Операции считаются
curl -s -H "Cookie: lk_session=<сессия>" https://corebridge.ru/lk/dashboard | jq '.operations_usage'

docker exec corebridge-postgres psql -U corebridge -d corebridge -c \
  "select counter_type, period, count, limit_value, is_limit_hit
     from platform.usage_counters where tenant_id = '<tenant>'"
```

## Что уже сделано на стороне сайта

- Прогресс-бары «Операций X / Y» на дашборде и в биллинге **не показывают факт** —
  только лимит тарифа, с подписью «до N». Выдумывать число нельзя; как появится
  `operations_usage`, заменю на настоящий бар одной правкой.
- Лимиты n8n на всех экранах ЛК берутся из `GET /lk/plans`, а не из `n8n_usage.limit` —
  обход пункта 2. После починки обход можно снять, но он безвреден.
- Уведомление `limit_exceeded` уже есть в матрице настроек и включается пользователем —
  ждёт только повода со стороны сервера.
