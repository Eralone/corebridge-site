# S15 — Удаление аккаунта не доходит до конца: audit_log стал неизменяемым

**Приоритет:** 🔴 вторая фаза удаления аккаунта падает. Клиент, потребовавший
удаления по 152-ФЗ, останется в `pending_deletion` навсегда, а ночной cron будет
падать на нём каждую ночь.
**Объём:** решение о том, как совместить неизменяемость журнала с обезличиванием.
Правка небольшая, но выбор за вами — вариантов три.

Найдено сквозным прогоном 2026-07-30: завёл настоящий аккаунт, прошёл путь клиента
и попытался вычистить за собой штатной механикой.

## Что происходит

```bash
$ docker exec corebridge-admin node -e "
  require('/app/src/services/admin/privacy_admin.service').purgeTenant('<id>')
    .catch(e => console.error(e.message))"

audit_log is immutable: UPDATE/DELETE forbidden
```

Тенант остаётся в `pending_deletion`, данные не вычищены.

## Причина — столкновение двух правильных решений

**Первое.** `purgeTenant()` обезличивает автора записей журнала — так и задумано,
это записано и в комментарии сервиса, и в `privacy.html` §6.3:

```js
// privacy_admin.service.js, purgeTenant()
await client.query(
  `UPDATE platform.audit_log SET actor = $2 WHERE tenant_id = $1 AND actor = $3`,
  [tenantId, `deleted_user:${u.id}`, `lk_user:${u.id}`]
);
```

**Второе.** На таблице стоит триггер, запрещающий любые изменения:

```sql
CREATE TRIGGER audit_log_immutable
  BEFORE DELETE OR UPDATE ON platform.audit_log
  FOR EACH ROW EXECUTE FUNCTION platform.deny_audit_modification();
```

Оба требования законны: журнал должен быть неподделываемым, персональные данные —
удаляемыми. Но вместе они делают вторую фазу невыполнимой.

**Почему это не всплыло раньше.** Падает только если у тенанта есть записи журнала
с `actor = 'lk_user:<id>'`. У свежего аккаунта без действий их нет, и чистка
проходит. Ночной cron всё это время писал `OK {"checked":0}` — просто потому,
что удалять было нечего:

```
2026-07-30T03:30:01+00:00 OK {"checked":0,"results":[]}
```

Первое же настоящее обращение на удаление упрётся в это.

## Три варианта, выбирать вам

**1. Разрешить триггеру именно обезличивание.** Пропускать UPDATE, если меняется
только `actor` и только с `lk_user:%` на `deleted_user:%`, всё остальное запрещать:

```sql
IF TG_OP = 'UPDATE'
   AND NEW.actor LIKE 'deleted_user:%' AND OLD.actor LIKE 'lk_user:%'
   AND ROW(NEW.*) IS NOT DISTINCT FROM ROW((OLD.*) #= hstore('actor', NEW.actor))
THEN RETURN NEW; END IF;
```

Просто, но делает журнал «почти неизменяемым», а это уже не то свойство,
ради которого триггер ставили.

**2. Не хранить в журнале персональные данные вовсе.** `actor` держать ссылкой
(`user_id`), а имя и почту брать из `platform.users` при чтении. Тогда удаление
пользователя само по себе обезличивает журнал, ничего менять не нужно.
Дороже — нужна миграция и правка чтения, — но снимает противоречие насовсем
и, на мой взгляд, единственный по-настоящему верный вариант.

**3. Отдельная привилегированная роль.** Обезличивание делает роль, которой
триггер не мешает (`SECURITY DEFINER`-функция). Работает, но фактически
оставляет чёрный ход в неизменяемый журнал.

## Второе, отдельное: обезличивается только `actor`, а почта лежит в `new_value`

Всплыло при фактической чистке тестового аккаунта. `purgeTenant` меняет `actor`,
но содержимое записи не трогает — а туда почта попадает при регистрации:

```sql
select action, new_value from platform.audit_log where tenant_id = '<id>';

     action      |                        new_value
-----------------+----------------------------------------------------------
 user_registered | {"email": "qa-e2@corebridge.ru", "company_name": null, …}
```

То есть даже после починки пункта выше адрес клиента останется в журнале
навсегда: `actor` станет `deleted_user:<id>`, а почта в `new_value` — нет.
Для настоящего обращения по 152-ФЗ это значит, что данные удалены не полностью.

Варианты те же по сути: либо не класть почту в журнал вовсе (достаточно
`user_id`, адрес читается из `platform.users`, пока пользователь есть), либо
обезличивать и `new_value` вместе с `actor`. Первое опять же чище — тогда
удаление пользователя само по себе очищает журнал от личных данных.

⚠️ Проверьте заодно остальные действия, которые пишут в `new_value`: если туда
попадают телефон, название компании или ИНН, вопрос тот же.

## Что ещё стоит поправить заодно

**Cron молчит о неудаче по существу.** `purgeExpired()` возвращает `results`,
но обёртка пишет в лог `OK`, даже если внутри у части тенантов были ошибки.
Стоит выводить количество неудач и падать с ненулевым кодом — иначе такая
поломка снова будет невидимой месяцами.

**Подтверждение удаления у безымянного тенанта.** `scheduleDeletion` требует
`confirm_company_name`; если названия нет, ожидается **`id` тенанта**, а не `null`.
Это разумно, но нигде не описано — я узнал это, получив `COMPANY_NAME_MISMATCH`.
Прошу дописать в `API_ENDPOINTS.md`.

## Как проверить, что починилось

```bash
# завести тенанта, сделать им хоть одно действие (чтобы появился журнал),
# затем пройти обе фазы целиком
docker exec corebridge-admin node -e "
const s=require('/app/src/services/admin/privacy_admin.service');
s.scheduleDeletion('<id>',{reason:'проверка',confirm_company_name:'<название или id>'},null,'admin@corebridge.ru')
 .then(()=>s.purgeTenant('<id>'))
 .then(r=>console.log('ok',JSON.stringify(r)))
 .catch(e=>console.error('ERR',e.message));"

# журнал должен остаться, но без личных данных
docker exec corebridge-postgres psql -U corebridge -d corebridge -c \
  "select actor, count(*) from platform.audit_log where tenant_id='<id>' group by 1"
# ожидаем deleted_user:… либо ссылку, но не lk_user:…
```
