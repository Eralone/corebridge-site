# Промт для локального claude-code в `corebridge-server` — пакет S2: привести каталог тарифов к канону сайта

> Передать целиком локальному claude-code в репозитории `corebridge-server`.
> **Решение продукта (Дмитрий, 2026-07-26): канон тарифов — `pricing.html` сайта.**
> Сайт прайс не хардкодит и берёт всё из `GET /lk/plans`, поэтому каталог на сервере надо
> привести к цифрам сайта. Составлено сайтом 2026-07-26 по фактической разметке `pricing.html`.

## Что не так сейчас

`GET /lk/plans` (реализован, `lk-api/src/config/plans.js`) отдаёт каталог, который **расходится**
с утверждённой страницей тарифов. Расхождения по каждому плану:

| Поле | Сейчас на сервере | Должно быть (канон `pricing.html`) |
|---|---|---|
| `trial.limits.monthly_operations` | 150 | **500** |
| `business.limits.users_per_company` | 5 | **3** |
| `professional.title` | «Профессиональный» | **«Профессионал»** |
| `professional.price.monthly` | 4 990 | **5 990** |
| `professional.limits.projects` | 30 | **20** |
| `professional.limits.monthly_operations` | 150 000 | **100 000** |
| `professional.limits.users_per_company` | 10 | **5** |
| `enterprise.title` | «Корпоративный» | **«Энтерпрайз»** |
| `enterprise.price.monthly` | 19 900 | **цена по запросу** (нужен флаг, см. §2) |
| формат `price.yearly` | годовая сумма (9 500 / 24 900 / 47 900) | нужна ещё цена «за месяц при годовой оплате», см. §3 |
| промо-акция | отсутствует | **professional: первые 30 дней за 10 ₽**, см. §4 |
| маркетинговые фичи | отсутствуют | `telegram_support`, `on_premise`, `sla`, см. §5 |

Совпадает и менять не надо: коды планов (`trial|starter|business|professional|enterprise`),
`trial` 0 ₽ / 1 проект / 1 пользователь, `starter` 990 ₽ / 3 проекта / 5 000 операций / 1 пользователь,
`business` 2 490 ₽ / 10 проектов / 30 000 операций, `enterprise` — без лимитов,
фича `n8n_ui` только у professional и enterprise.

## 1. Целевая матрица (источник — `pricing.html`, сверено с таблицей «Сравнение тарифов»)

| Название (`title`) | код | ₽/мес | ₽/мес при годовой | ₽/год | Интеграций (`projects`) | Операций/мес | Пользователей | `n8n_ui` |
|---|---|---|---|---|---|---|---|---|
| Пробный | `trial` | 0 | — | — | 1 | **500** | 1 | ❌ |
| Старт | `starter` | 990 | 792 | 9 504 | 3 | 5 000 | 1 | ❌ |
| Бизнес | `business` | 2 490 | 1 992 | 23 904 | 10 | 30 000 | **3** | ❌ |
| **Профессионал** | `professional` | **5 990** | **4 792** | **57 504** | **20** | **100 000** | **5** | ✅ |
| **Энтерпрайз** | `enterprise` | по запросу | — | — | ∞ (99999) | ∞ | ∞ | ✅ |

Годовая цена = помесячная − 20 % (проверено: 990·0,8=792, 2490·0,8=1992, 5990·0,8=4792).
Годовая сумма = цена «за месяц при годовой» × 12.

**Лимиты, которых на странице тарифов нет** — `n8n_executions_month`, `n8n_concurrent`,
`log_retention_days` — оставить как на сервере, сайт их не показывает.

⚠️ Матрицу `PLAN_LIMITS` в `license-service/src/jwt-generator.js` (то, что кладётся в JWT и по чему
реально работают лимиты) надо поправить **синхронно** с `lk-api/src/config/plans.js` — иначе сайт
покажет одно, а .epf получит в токене другое. Это важнее косметики.

## 2. Enterprise «по запросу» — нужен флаг

На странице у Энтерпрайза вместо цифры написано «По запросу», а вместо кнопки оплаты — ссылка
`mailto:info@corebridge.ru`. Сайту нужно уметь это отличить, не хардкодя код плана.

```
GET /lk/plans → plans[]: {
  ...,
  "price": { "monthly": null, "yearly": null, ... },
  "is_custom_price": true,          // ← НОВОЕ поле; у остальных планов false
  "contact_email": "info@corebridge.ru"   // ← опционально, иначе сайт возьмёт из конфига
}
```

Заодно решить: должен ли `POST /lk/billing/pay` отклонять `plan=enterprise`?
**Просьба сайта: да** — возвращать `400 CUSTOM_PRICE_PLAN`, чтобы кнопка оплаты для enterprise
не могла быть нажата случайно.

## 3. Формат цен — добавить цену «за месяц при годовой оплате»

Переключатель «Помесячно / Ежегодно −20 %» на странице показывает именно **месячную** цену при
годовой оплате (в разметке `data-m="990" data-y="792"`), а сервер сейчас отдаёт годовую сумму.
Чтобы сайт не считал сам (иначе округления разъедутся), нужно:

```
"price": {
  "monthly": 990,            // ₽/мес при месячной оплате
  "yearly_monthly": 792,     // ← НОВОЕ: ₽/мес при годовой оплате (то, что показывает тумблер)
  "yearly": 9504,            // ₽ за год целиком (списывается при оплате period=yearly)
  "discount_percent": 20     // ← НОВОЕ: для подписи «−20%»
}
```

Существующее поле `yearly` сохранить (обратная совместимость), но привести к каноничным суммам:
starter **9 504**, business **23 904**, professional **57 504** (сейчас 9 500 / 24 900 / 47 900).

## 4. Промо-акция «первые 30 дней за 10 ₽» (только professional)

На странице у Профессионала в описании: «Первые 30 дней за 10 рублей», кнопка называется
«Попробовать», а не «Оплатить». Механики промо на сервере нет вообще.

Нужно решение с твоей стороны — как это реализовать. Предложение сайта, минимальный вариант:

```
GET /lk/plans → plans[]: {
  ...,
  "promo": {                                 // ← НОВОЕ, null у остальных планов
    "code": "first30",
    "label": "Первые 30 дней за 10 ₽",
    "price": 10,
    "period_days": 30,
    "cta_label": "Попробовать",
    "once_per_tenant": true                  // повторно тому же tenant не даём
  }
}
```

И в оплате:

```
POST /lk/billing/pay   body { "plan":"professional", "period":"monthly", "promo":"first30" }
→ создаёт платёж на 10 ₽ и лицензию на 30 дней
errors: 409 PROMO_ALREADY_USED · 400 PROMO_NOT_APPLICABLE (промо не для этого плана/периода)
```

Вопросы, на которые нужен твой ответ:
- что происходит **после** 30 дней за 10 ₽ — автопродление по полной цене (нужна подписка в
  Robokassa) или лицензия просто истекает и пользователь платит вручную? Сайту надо это
  корректно написать в интерфейсе;
- храним ли факт использования промо (нужна колонка/таблица), чтобы `once_per_tenant` работал.

Если промо — большая работа, скажи: сайт временно покажет текст «Первые 30 дней за 10 ₽» как
статичную подпись без работающей кнопки промо-оплаты, а полную механику вынесем в бэклог.
**Но тогда это надо явно решить, а не молча разойтись.**

## 5. Маркетинговые признаки для таблицы «Сравнение тарифов»

Таблица на странице содержит строки, которых нет в `features`:

| Строка таблицы | trial | starter | business | professional | enterprise | предлагаемый ключ |
|---|---|---|---|---|---|---|
| Поддержка в Telegram | − | − | ✓ | ✓ | ✓ | `telegram_support` |
| On-premise (свой сервер) | − | − | − | − | ✓ | `on_premise` |
| SLA 99.95 % | − | − | − | − | ✓ | `sla` |
| Все 4 конфигурации 1С | ✓ | ✓ | ✓ | ✓ | ✓ | (у всех — не нужен флаг) |
| Полный каталог (33 сервиса) | ✓ | ✓ | ✓ | ✓ | ✓ | (у всех — не нужен флаг) |

Добавить эти три ключа в `features` каталога `GET /lk/plans`. **Важно:** это чисто отображаемые
признаки, в JWT (`PLAN_LIMITS.features`) их тащить не нужно — там только то, что проверяет код.
Если удобнее отдать их отдельным объектом (`marketing_features`), а не в `features` — скажи, сайт
подстроится.

## 6. Найденное противоречие внутри самого дизайна — нужно продуктовое решение

В `pricing.html` FAQ написано: «На **Энтерпрайзе** вы получаете доступ к отдельному интерфейсу n8n
внутри личного кабинета», а карточки планов и таблица сравнения дают «Прямой доступ к n8n UI»
**и Профессионалу, и Энтерпрайзу**. Сервер сейчас согласен с карточками
(`features.n8n_ui = true` у professional и enterprise).

**Сайт исходит из карточек и таблицы** (их два против одного упоминания в FAQ) и поправит текст FAQ.
Если верно обратное — сообщи, тогда `n8n_ui` у professional надо снять, а это меняет и ценность
тарифа, и лимиты.
