# S18 — Вход через Яндекс ID не доводит до кабинета, письма не уходят вообще

**Приоритет:** 🔴 задета входная дверь продукта. Человек регистрируется и
оказывается обратно на форме входа; ни одно письмо с платформы не отправлено
ни разу.
**Объём:** одна строка кода + две строки в `.env`.

Найдено 2026-07-31 при разборе жалобы «новый аккаунт на сайте не создаётся».
Жалоба справедливая по ощущениям и неверная по факту: **аккаунты создаются**.

---

## 1. 🔴 `SameSite=Strict` роняет вход после возврата от Яндекса

### Что видит человек

Нажимает «Зарегистрироваться через Яндекс ID», подтверждает в Яндексе,
возвращается — и видит форму входа. Выглядит как «регистрация не сработала».

### Что происходит на самом деле

Аккаунт создан, сессия жива. Вот запись из боевой базы — ровно момент возврата:

```
email               | auth_provider | email_verified | created_at
eralonecb@yandex.ru | yandex        | t              | 2026-07-30 21:05:53+00
```

И тот же момент в логе nginx:

```
21:05:43  GET /lk/auth/yandex                 302   → oauth.yandex.ru
21:05:53  GET /lk/auth/yandex/callback        302   → cookie поставлена, ведёт в кабинет
21:05:53  GET /dashboard                      307   ← cookie НЕ пришла, guard разворачивает
21:05:53  GET /login?next=%2Fdashboard        200   ← приехали обратно на вход
```

Причина — `server/src/routes/lk/auth.routes.js:31`:

```js
const COOKIE_OPTS = {
  httpOnly: true,
  sameSite: 'strict',        // ← вот здесь
  secure: process.env.NODE_ENV === 'production',
  maxAge: SESSION_TTL * 1000,
  path: '/',
};
```

Cookie со `Strict` браузер **не отправляет** в запросе, который возник из
перехода с чужого сайта. Возврат из OAuth — именно такой переход: цепочка
начата на `oauth.yandex.ru`, и весь её хвост, включая `GET /dashboard`,
считается сторонним. Cookie при этом **сохраняется** — не отправляется только
в этом переходе.

### Проверено опытом, а не по спецификации

Завёл живую сессию и сравнил два перехода на одну и ту же закрытую страницу:

```
cookie lk_session: sameSite=Strict, secure=false, httpOnly=true

переход внутри сайта    → /dashboard              (пускает)
переход с чужого origin → /login?next=%2Fdashboard (разворачивает)
```

Второй случай — буквально то, что делает Яндекс.

### Как чинить

```js
sameSite: 'lax',
```

`Lax` отправляет cookie при переходах верхнего уровня по GET (ровно наш
случай) и по-прежнему **не** отправляет её при межсайтовых POST — то есть
защита от CSRF, ради которой ставили `Strict`, остаётся. Это стандартный
выбор для сессионной cookie на сайте с OAuth.

### ⚠️ Тем же болеет вход по ссылке из письма

`auth.routes.js:194` — magic-link ставит cookie и ведёт в кабинет тем же
приёмом. Ссылку открывают из почты, то есть переход **всегда** межсайтовый.
Значит вход по ссылке не работает ни разу, просто это некому было заметить:
письма (см. §2) всё равно не уходят. После правки `sameSite` починятся оба.

### Что сделано на моей стороне (временно)

Чтобы дверь не стояла закрытой до вашего деплоя, добавил обход в сайте:
кнопка «Войти через Яндекс ID» помечает попытку в `sessionStorage`, и если
человек вернулся на форму входа с `?next=`, делается **один** переход внутри
сайта — cookie уходит, guard пускает.

```
Путь после возврата с чужого сайта:
  → /login?next=%2Fdashboard
  → /dashboard                  ✓ человек в кабинете

Аноним без метки: /login?next=%2Fdashboard  ✓ форма входа, как и должно
```

Обход ровно одноразовый, живёт 2 минуты и обычных посетителей не задевает.
Файл `lib/auth/oauth-return.ts`, помечен как временный — **после `lax` его
удалю.**

## 2. 🔴 Почта не отправлена ни разу: сертификат не совпадает с адресом релея

### Симптом

```json
{"level":"error","event":"email_send_failed",
 "subject":"Подтвердите email в CoreBridge",
 "code":"ESOCKET","command":"CONN",
 "msg":"Hostname/IP does not match certificate's altnames: IP: 172.21.0.1 is not in the cert's list: "}
```

За всё время в логах `lk-api`: **успешных отправок — 0**.

Отсюда же `verification_sent: false` в ответе `POST /lk/auth/register` —
не флаг «потом отправим», а честное «не отправилось».

### Причина

```
SMTP_HOST=172.21.0.1     ← адрес шлюза docker-сети, то есть Postfix на хосте
SMTP_PORT=25
```

Postfix на хосте живой, STARTTLS предлагает и представляется по имени:

```
220 mail.corebridge.ru ESMTP Postfix (Ubuntu)
250-STARTTLS
```

А сертификат у него — веб-сертификат сайта:

```
subject = CN = corebridge.ru
SAN     = DNS:corebridge.ru, DNS:www.corebridge.ru
```

Ни `mail.corebridge.ru`, ни тем более IP там нет. nodemailer поднимает
STARTTLS, сверяет сертификат с `172.21.0.1`, не находит совпадения и рвёт
соединение. Письма не уходят **никакие**: подтверждение почты, сброс пароля,
ссылка для входа, приглашения в команду.

### Как чинить

В коде уже есть нужный переключатель — `auth.service.js`:

```js
if (process.env.SMTP_TLS_INSECURE === 'true') {
  options.tls = { rejectUnauthorized: false };
}
```

Достаточно `.env`:

```bash
SMTP_TLS_INSECURE=true
```

Релей локальный: трафик идёт по внутреннему мосту docker и хост не покидает,
так что проверка имени тут ничего не охраняет. Заодно стоит поставить
`SMTP_SKIP_AUTH=true` — Postfix на порту 25 для своих сетей аутентификацию
не объявляет, а `SMTP_USER`/`SMTP_PASS` заданы, и nodemailer может упасть
на «No supported authentication method(s) available» уже после того, как
разберётесь с TLS.

Долгий вариант, если хочется настоящей проверки: выпустить сертификат на
`mail.corebridge.ru`, отдать его Postfix и указать `SMTP_HOST=mail.corebridge.ru`
с резолвом на адрес моста. Ради локального релея — избыточно, но решать вам.

### Как проверить

```bash
docker logs corebridge-lk-api -f | grep email_
# ожидаем event":"email_sent", а не email_send_failed
```

## 3. 🟠 На проде `NODE_ENV=development`

Всплыло по дороге: сессионная cookie пришла **без флага `Secure`**. Причина —
`secure: process.env.NODE_ENV === 'production'`, а в боевых контейнерах:

```
corebridge-lk-api            NODE_ENV=development
corebridge-bridge            NODE_ENV=development
corebridge-admin             NODE_ENV=development
corebridge-license-service   NODE_ENV=development
```

Источник — `/opt/corebridge/.env:39`.

Сайт работает только по HTTPS и отдаёт HSTS, так что практический риск сейчас
невелик. Но флаг — последняя преграда, если однажды появится ссылка по
`http://`, и держать его выключенным на боевой машине незачем.

Проверил, не течёт ли наружу что-то ещё: обработчик ошибок аккуратный, стек
не отдаёт (`POST /lk/auth/login` с битым JSON → `{"error":"INTERNAL_ERROR"}`).
То есть беспокоит именно cookie.

Прошу `NODE_ENV=production` — но **после** проверки: смена режима у Express
задевает не только это (кэш шаблонов, подробность ошибок), и лучше прогнать
ваши наборы тестов в этом режиме, чем менять вслепую перед выходными.

## 4. Что перепроверено и работает

Чтобы не искали там, где цело:

- `POST /lk/auth/register` — 201, аккаунт заводится, сессия ставится, кабинет
  открывается. Проверено и curl, и живым браузером до самого дашборда.
- Регистрация паролем через форму сайта — доходит до конца.
- Выкладка `.epf` после ваших S16/S17 — все четыре конфигурации выложены,
  размеры и контрольные суммы сошлись с вашей таблицей, скачивание по
  одноразовому токену работает, повтор даёт 410.

## 5. Порядок, если чинить по одному

1. `SMTP_TLS_INSECURE=true` — письма пойдут сразу, деплоя кода не нужно.
2. `sameSite: 'lax'` — чинит и Яндекс ID, и вход по ссылке.
3. `NODE_ENV=production` — после прогона тестов.
