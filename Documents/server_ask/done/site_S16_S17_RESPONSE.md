## 1. S17 — причина оказалась не в коде

Симптом вы описали точно. Но вывод «ошибка в коде, перегрузки в схеме нет»
верен только для прода. В репозитории перегрузка **есть** — она объявлена
в `db/migrations/011_epf_versions.sql:64`, и локально с ней всё работало:

```
$ psql -c "\df platform.activate_epf_version"
 activate_epf_version(p_version_id uuid)
 activate_epf_version(p_config text, p_version text)   ← локально есть, на проде нет
```

Расхождение объясняет история файла:

```
6d9f4e4  2026-04-06  файл 011 создан           — только сигнатура (uuid)
571a1f5  2026-04-08  в ТОТ ЖЕ файл 011 дописан блок с перегрузкой (text, text)
```

Между этими датами 011 успели накатить. `db/migrate.js` сверял только **номер
версии**, поэтому при следующем запуске честно написал `= Already applied: 011`
и дописанный блок не выполнил — никогда. Прод остался с одной сигнатурой,
рабочие машины и CI — с двумя.

Отсюда и то, что вы отметили как странность: тест на моке проходил, потому что
мок сигнатур не знает. Но дефект прятал не только тест — его прятал и сам
менеджер миграций, который считал 011 применённой полностью.

### Что сделано

**1.1. Код переведён на сигнатуру `(UUID)`** — единственную, которая есть во
всех окружениях (`server/services/epf/epf_version.service.js:85`).

Мы взяли ваш **второй** вариант — искать id внутри `activate()`, — а не первый.
Причина: сигнатуру метода менять нельзя. Вызовов четыре, а id есть только у
выкладки:

| Вызов | Что знает |
|---|---|
| `server/routes/public/epf_publish.routes.js:106` | config, version, **id** от `register()` |
| `server/routes/admin/epf.admin.routes.js:126` | только config + version |
| `scripts/epf/publish_epf.js:130` | только config + version |
| `scripts/epf/publish_epf_local.js:150` | только config + version |

Предложенный `activate(config, version, versionId)` починил бы выкладку и молча
сломал бы активацию из админ-панели: три вызывающих передают два аргумента,
`versionId` пришёл бы `undefined`. Внутренний поиск id закрывает все четыре.

Заодно активация теперь падает **до** изменения данных, если версии нет:

```js
if (!rows.length) {
  throw new Error(`epf_version not found: config=${config}, version=${version}`);
}
```

Прежняя перегрузка сначала снимала `is_active` со старой версии и только потом
проверяла, что новая существует. При опечатке в версии конфигурация осталась бы
вообще без активной сборки — клиенты перестали бы получать обновления.

**1.2. Миграция `028_epf_activate_single_signature.sql`** — снимает перегрузку
`(TEXT, TEXT)` там, где она есть. На проде это no-op (`DROP ... IF EXISTS`),
на рабочих машинах убирает лишний объект. После неё схема во всех окружениях
одинаковая — ровно одна сигнатура.

**1.3. Тест `server/tests/epf_cdn.test.js:209` переписан.** Вы правы, он держал
баг. Теперь он проверяет поиск id, вызов с одним аргументом и **отдельно** —
что вызова с двумя аргументами не происходит ни в каком виде. Плюс тест на
понятную ошибку при отсутствующей версии.

**1.4. Главное — чтобы это не повторилось.** `db/migrate.js` теперь хранит
sha256 содержимого каждой миграции и сверяет его при `up` и `status`:

```
$ node db/migrate.js status
  ⚠ DRIFT    011_epf_versions.sql  (файл изменён после накатывания)
  ⚠ Изменено после накатывания: 1 — оформите правку новой миграцией.

$ node db/migrate.js up
✗ Применённые миграции изменены после накатывания:
  011_epf_versions.sql
    накатывали: 7729f9b22156…
    в файле:    49513e395f5d…
  Править применённую миграцию нельзя: номер версии не меняется, ...
$ echo $?
1
```

Деплой при таком расхождении **останавливается** — `deploy.sh` вызывает
`migrate.js up`. Escape-hatch для заведомо косметических правок:
`MIGRATIONS_ALLOW_DRIFT=1`.

Первый запуск после этой правки расхождений не покажет: суммы у уже
применённых миграций фиксируются как точка отсчёта (что накатывали месяц
назад — уже не восстановить). Ловиться будут правки, сделанные с этого момента.

Проверили привычку по всей истории: **12 файлов миграций правились после
создания**. Большинство — апрельская возня до боевого запуска, но 011 (08.04)
и 023 (27.07) уже могли разъехаться. Теперь такое не проходит молча.

**1.5. Побочно — команда `baseline`.** Наша локальная база оказалась
рассинхронизирована ровно так же: 019–022 применяли мимо `migrate.js`, записи
о них не было, и `up` пытался накатить их повторно — падал на
`trigger ... already exists` в 023. Раньше это чинили руками в psql, что и
порождает такие истории. Теперь:

```bash
node db/migrate.js baseline 023_notification_templates 024_2fa_and_privacy
# ✓ Отмечена применённой (SQL не выполнялся)
```

## 2. S16 — правка компоуза

Ваша проверка была верной, но причина не в потерянной правке. Хронология:

| Время (31.07) | Событие |
|---|---|
| 04:44 | деплой: миграция 027 + лимит nginx для `/api/v1/epf/` |
| ~18:00 | вы смотрите сервер, видите `:ro` — **справедливо**, правки ещё нет |
| 18:07 | коммит `22c9afa`: `:ro` → rw у bridge + ваши промты S16/S17 |

То есть правка компоуза и промт, сообщающий об её отсутствии, приехали в
репозиторий одним коммитом. На сервере её не было потому, что деплоя после
18:07 ещё не случалось, — а не потому, что она потерялась.

Что деплой 04:44 доехал, мы проверили на живом проде:

```bash
$ curl -X POST https://api.corebridge.ru/api/v1/epf/publish \
    -H "Authorization: Bearer ***" -F "file=@1.3МБ" -F "config=НЕВЕРНЫЙ" ...
{"error":"invalid_config","allowed":["ut11","unf","ka","bp"]}   # 400, не 413
```

400 вместо 413 — значит лимит `client_max_body_size 60m` применён.

**Ближайший деплой довозит rw-монтирование**, после чего ваше наложение
`epf-rw.override.yml` можно снимать. `lk-api` и `nginx` остаются `:ro` — они
только читают, как вы и предполагали.

### 2.1. Права каталога забрали в репозиторий

Спасибо, что подсветили: это действительно держалось на вашей ручной команде
и потерялось бы. Добавлено в `scripts/deploy.sh` (шаг 2b, до подъёма сервисов):

```bash
EPF_DIR="/opt/corebridge/epf"
log "Каталог сборок .epf: ${EPF_DIR}"
mkdir -p "${EPF_DIR}"
chmod o+x "${EPF_DIR}"
```

С комментарием, объясняющим связь `X-Accel-Redirect` → `alias` → `www-data` →
403, — чтобы следующий, кто увидит `Permission denied` при исправной выдаче
токена, не искал заново. Только `+x`, без `+r`: листинг не открывается.

## 3. Как проверить после ближайшего деплоя

```bash
# 1. Том на запись — уже без вашего наложения
docker inspect corebridge-bridge \
  --format '{{range .Mounts}}{{if eq .Destination "/opt/corebridge/epf"}}rw={{.RW}}{{end}}{{end}}'
# rw=true

# 2. Права каталога выставлены деплоем
stat -c '%A %U:%G' /opt/corebridge/epf     # drwxr-x--x deploy:deploy

# 3. В базе одна сигнатура
docker exec corebridge-postgres psql -U corebridge -d corebridge -c \
  "\df platform.activate_epf_version"
# ровно одна строка: activate_epf_version(p_version_id uuid)

# 4. Выкладка проходит целиком
curl -sS -o /dev/null -w '%{http_code}\n' -X POST \
  https://api.corebridge.ru/api/v1/epf/publish \
  -H "Authorization: Bearer $ADMIN_API_KEY" \
  -F "file=@dist/unified_unf.epf" -F "config=unf" -F "version=v1.0.0"   # 200

docker exec corebridge-postgres psql -U corebridge -d corebridge -c \
  "SELECT config, version, is_active, file_size FROM platform.epf_versions
    WHERE is_active ORDER BY config;"
```

По заглушкам `0.0.1` у `unf`, `ka`, `bp`: они снимутся сами, когда воркфлоу
доедет до этих конфигураций — активация ставит `is_active = FALSE` всем
остальным версиям того же `config` внутри одной транзакции.

Неактивные строки, оставшиеся на проде от падавших попыток, удалять не нужно:
они не мешают (`getActive` смотрит только `is_active = TRUE`) и служат историей
версий. Если захотите прибраться — только те, у которых `file_size < 50000`.
