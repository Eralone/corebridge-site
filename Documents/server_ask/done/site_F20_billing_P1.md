## 0. Главное в двух абзацах

До сегодняшнего дня **оплатить тариф в CoreBridge было физически невозможно**. Каркас
биллинга существовал с 2024 года, но не работал ни в одной точке: `InvId` генерировался
строкой (Robokassa принимает только целое число — платёжная форма не открывалась), уведомление
об оплате уходило не в тот сервис, ответ вебхука был в неверном формате, а статусы платежей
не совпадали между тремя сервисами. Сейчас всё это починено: клиент может оплатить тариф
и получить лицензию.

**Но открывать кнопку «Оплатить» реальным клиентам ещё рано** — см. §6. Сейчас от сайта нужна
готовность страниц, а не их публикация. Отдельно и срочно: **подпись платежа считается только
на сервере** (§4) — это единственное место, где ошибка на фронте стоит денег.

## 2. `POST /lk/billing/pay`

**Запрос**

```json
{
  "plan": "professional",     // trial | starter | business | professional (enterprise → 400)
  "period": "monthly",        // monthly | yearly
  "promo": "first30",         // опционально
  "autopay": true             // опционально: сделать платёж референтным для автосписаний
}
```

**Ответ 200**

```json
{
  "payment_url": "https://auth.robokassa.ru/Merchant/Index.aspx?MerchantLogin=…",
  "payment_params": {
    "MerchantLogin": "Corebridge",
    "OutSum": "5990.00",
    "InvId": "1042",
    "Description": "CoreBridge — подписка «Профессионал», 1 мес.",
    "SignatureValue": "A1B2C3…",
    "Recurring": "true"
  },
  "payment_id": "pay_V1StGXR8Z5jdHi6B",
  "external_payment_id": "1042",
  "amount": 5990,
  "promo": null,
  "autopay": true
}
```

- **`payment_url`** — готовая ссылка, можно просто редиректить.
- **`payment_params`** — те же параметры для встраивания в виджет (§4).
- **`payment_id`** — идентификатор для ссылок и поллинга. **Наружу используйте только его**:
  `InvId` последователен, по нему перебираются чужие платежи.
- Если платёжная система не настроена, придёт `{"payment_url": null, "message": "Платёжная система настраивается"}` — покажите это сообщение, а не пустую страницу.

**Ошибки**

| Код | HTTP | Когда |
|---|---|---|
| `MISSING_FIELDS` | 400 | нет `plan` или `period` |
| `INVALID_PLAN` / `INVALID_PERIOD` | 400 | значение вне словаря |
| `CUSTOM_PRICE_PLAN` | 400 | «Энтерпрайз» — цена по запросу, ведите на форму контактов |
| `PROMO_NOT_APPLICABLE` | 400 | промо не подходит к тарифу/периоду |
| `PROMO_ALREADY_USED` | 409 | промо уже использовано этим тенантом |
| `TOO_MANY_REQUESTS` | 429 | больше 20 создания платежей в час на тенанта |

**Повторные клики безопасны.** Живая ссылка (моложе 30 минут, тот же тариф и период)
переиспользуется, а не плодит новые счета — `payment_id` вернётся прежний. Отдельная защита
на фронте не нужна, но кнопку на время запроса лучше блокировать.

## 3. Статус платежа и возврат с Robokassa

### 🔴 Success-возврат **ничего не подтверждает**

Единственный авторитет оплаты — серверное уведомление ResultURL, которое Robokassa шлёт
напрямую на API. Возврат пользователя на SuccessURL подделывается тривиально. Поэтому:

1. Пользователь возвращается на `https://corebridge.ru/lk/billing/success` (уже прописано
   в кабинете Robokassa).
2. Страница показывает «Платёж обрабатывается» и **опрашивает** `GET /lk/billing/:public_id`.
3. Как только `status` стал `paid` — показываем успех и обновлённый тариф.

`payment_id` для поллинга сохраните перед редиректом (sessionStorage или query-параметр
вашего собственного URL — не полагайтесь на то, что Robokassa его вернёт).

**Ответ `GET /lk/billing/:public_id`**

```json
{
  "public_id": "pay_V1StGXR8Z5jdHi6B",
  "amount": "5990.00",
  "currency": "RUB",
  "status": "pending",
  "plan": "professional",
  "period": "monthly",
  "payment_method": null,
  "paid_at": null,
  "failure_reason": null,
  "created_at": "2026-08-05T12:00:00.000Z"
}
```

404 `PAYMENT_NOT_FOUND` — платежа нет либо он чужого тенанта.

**Словарь статусов** (единый для всей платформы):

| Статус | Что показать пользователю |
|---|---|
| `pending` | «Платёж обрабатывается» + продолжать поллинг |
| `paid` | «Оплачено», тариф активен |
| `failed` | «Оплата не прошла», кнопка повторить |
| `expired` | ссылка протухла, создать платёж заново |
| `refunded` | «Возврат оформлен» |
| `mismatch` | **«Платёж требует проверки, мы свяжемся с вами»** — сумма не совпала с выставленной, лицензия сознательно не выдана. Не предлагайте платить ещё раз |

**Разумный поллинг:** каждые 2 секунды первые 30 секунд, дальше каждые 5 секунд, стоп через
2–3 минуты с сообщением «Обработка занимает больше обычного, мы напишем на почту».
Уведомление обычно приходит за секунды, но при сбое сети у Robokassa может задержаться.

Fail-возврат — `https://corebridge.ru/lk/billing/fail`, простая страница «Оплата не завершена»
с кнопкой вернуться к тарифам.

## 4. 🔴 Виджет Robokassa: подпись только с сервера

Во многих примерах интеграции виджета подпись считают в браузерном JS. **Так делать нельзя:**
это означает `Password1` магазина в исходниках страницы, и любой посетитель сможет выписать
себе «Профессионал» за 1 ₽ — подпись сойдётся, сервер примет.

Правильный порядок:

1. фронт зовёт `POST /lk/billing/pay`;
2. получает готовый `payment_params` с уже посчитанной `SignatureValue`;
3. передаёт эти параметры в виджет **как есть**, ничего не пересчитывая и не дополняя.

Если в коде сайта появится `MD5(...)`, `crypto-js` или любая переменная с `password` в имени
рядом с Robokassa — это ошибка, откатывайте.

Параметр `Receipt` (чек 54-ФЗ) сейчас **не приходит**: фискализация выключена. Когда включим,
он появится в `payment_params` уже URL-encoded — **не кодируйте его повторно**, подпись
перестанет сходиться. Просто передавайте всё, что пришло.

## 5. История операций

`GET /lk/billing` возвращает массив (последние 50, новые сверху):

```json
[{
  "public_id": "pay_V1StGXR8Z5jdHi6B",
  "amount": "5990.00",
  "currency": "RUB",
  "status": "paid",
  "plan": "professional",
  "period": "monthly",
  "description": "CoreBridge — подписка «Профессионал», 1 мес.",
  "payment_method": "BankCard",
  "is_recurring": false,
  "paid_at": "2026-08-05T12:00:12.000Z",
  "refunded_at": null,
  "refund_amount": null,
  "failure_reason": null,
  "created_at": "2026-08-05T12:00:00.000Z"
}]
```

**Про данные карт.** `payment_method` — это способ оплаты (`BankCard`, `SBP`, …), **не реквизиты**.
Платформа номеров карт не получает и не хранит: Robokassa их нам не передаёт. На странице
истории уместна явная плашка «Мы не храним данные вашей карты — оплата проходит на стороне
Robokassa». Это правда, и её стоит сказать вслух.

## 6. ⛔ Чего пока НЕ делать

**Не публикуйте кнопку «Оплатить» реальным пользователям.** Сервер умеет принять деньги, но
до этапа P1 клиента ждут неприятности:

- **оплата заранее сжигает остаток текущего периода** — срок считается от «сейчас», а не от
  конца оплаченного (исправляется в P1-4). Это прямой денежный ущерб клиенту;
- **письма об успешной оплате не отправляются** — шаблонов биллинга в диспетчере ещё нет (P1-6);
- **потерянное уведомление некому подобрать** — если ResultURL не дойдёт, платёж навсегда
  останется `pending` (сверка через `OpStateExt` — P1-3);
- **фискализация выключена** — вопрос чеков по 54-ФЗ владелец уточняет у бухгалтера.

Поэтому задача сайта сейчас — **подготовить страницы и спрятать их за флагом** (env-переменная
или feature flag). Порядок включения: сервер выкатывает P1 → владелец проводит живой тестовый
платёж → флаг снимается.

**Автоплатёж не показывайте вовсе.** Подписки Robokassa на модерации, `autopay: true`
сейчас проставит `Recurring` в платёж, но списывать по нему нечем — планировщика ещё нет (P2).
Галочку сверстайте, но держите скрытой до отдельного сигнала.

### 9.1 Метод SuccessURL/FailURL — вы правы, исправлено в кабинете

`SameSite=Lax` действительно не отдаёт cookie при межсайтовом POST-переходе, и клиент
после успешной оплаты попал бы на форму входа. В кабинете Robokassa метод задаётся
**отдельно для каждого из трёх URL**, поэтому конфликта нет:

| URL | Метод | Почему |
|---|---|---|
| Result URL | **POST** | server-to-server, cookie в цепочке нет |
| Success URL | **GET** | нужен переход, чтобы уехала сессионная cookie |
| Fail URL | **GET** | то же |

Обработчик ResultURL принимает и GET, и POST, так что здесь мы не связаны.

### 9.2 Адреса возврата — переходим на канонические `/billing/*`

Ваше предложение из §8.1 принимаю: в кабинете ставим
`https://corebridge.ru/billing/success` и `https://corebridge.ru/billing/fail`.
Это снимает совпадение с `:public_id` в корне, а не маскирует его порядком location.
Точные `location` для `/lk/billing/*` можете оставить как запасной путь — ломаться
нечему, но опираться мы на них больше не будем.

**Со своей стороны тоже подстраховался**: параметр маршрута ограничен префиксом
`pay_` — `router.get('/:public_id(pay_[A-Za-z0-9_-]+)')`. Теперь `/lk/billing/success`
не совпадает с маршрутом в принципе и уходит в 404 роутера, не доходя до БД.
Полагаться на чужой nginx для развязки собственных маршрутов было неправильно.
Покрыто тестом: «адреса возврата Robokassa не перехватываются как public_id».

### 10.1 Категория `billing` в настройках уведомлений — **готова, п. 7 вашего списка можно делать**

`GET /lk/notifications/settings` теперь возвращает в матрице пятую строку:

```json
{
  "matrix": {
    "billing":            { "email": true,  "telegram": false },
    "integration_errors": { "email": true,  "telegram": false },
    "limit_exceeded":     { "email": true,  "telegram": false },
    "reports":            { "email": false, "telegram": false },
    "news":               { "email": true,  "telegram": false }
  }
}
```

`PUT` принимает её так же, как остальные. Никаких новых полей и форматов.

**Название для интерфейса:** «Оплата и подписка».

🔴 **Просьба по формулировке.** Категория выключается, как и любая другая, — это
аккаунт клиента и его выбор. Но под ней лежат не только приятные письма об оплате,
а ещё и предупреждения «подписка заканчивается через 7/3/1 день». Политика продукта —
блокировка по истечении **без grace-периода**, поэтому выключивший эту категорию
клиент однажды обнаружит вставшие интеграции без единого предупреждения.

Напишите это прямо рядом с переключателем — например: «Сюда же приходят
предупреждения об окончании подписки. Если выключить, мы не сможем предупредить,
что доступ вот-вот приостановится». Скрытых исключений на сервере я делать не стал:
переключатель, который делает вид, что выключается, — хуже честного предупреждения.

Тексты писем лежат в БД и правятся `UPDATE`-ом без передеплоя, так что формулировки
можно доводить отдельно от кода.

### 10.3 Изменения в поведении, которые вас касаются

**Продление больше не сжигает остаток.** Оплата за неделю до окончания добавляет
месяц **к остатку**, а не вместо него. Если вы где-то показываете «новая дата
окончания» до оплаты — считайте её от текущего `valid_until`, а не от сегодня.
Оговорка: при **смене** тарифа остаток по-прежнему сгорает (пропорциональный
пересчёт — задача P3-2). Если на странице оплаты есть выбор другого тарифа,
об этом честнее предупредить.

**Зависшие платежи разбираются сами.** Раз в 15 минут сервер спрашивает у Robokassa

Ваш поллинг это увидит сам — правок не нужно. `pending` старше суток закрывается
как `expired`; ваша отрисовка этого статуса уже готова.
