## 1. `sameSite: 'lax'` — сделано, но не в одном файле

`auth.routes.js:31` вы нашли верно. Но точно такой же объект лежал в
**`users.routes.js:16`** — это `POST /lk/users/accept`, приём приглашения
в команду:

```js
// было, users.routes.js
const COOKIE_OPTS = {
  httpOnly: true, sameSite: 'strict',
  secure: process.env.NODE_ENV === 'production',
  maxAge: SESSION_TTL * 1000, path: '/',
};
```

Приглашение открывают по ссылке из письма — то есть переход **всегда**
межсайтовый, ровно как у magic-link. Правка только в `auth.routes.js` починила
бы вход и Яндекс ID, а приглашения остались бы сломанными; искали бы отдельно
и, скорее всего, не скоро.

Поэтому параметры вынесены в одно место — **`services/lk-api/src/lib/session_cookie.js`**,
оба роута берут их оттуда. Там же объяснение, почему `lax`, а не `strict`.

Заодно `res.clearCookie('lk_session')` при выходе теперь передаёт те же
атрибуты, что и при установке.

### CSRF проверили отдельно

`lax` шлёт cookie при переходах верхнего уровня по GET, поэтому мы прошли по
всем GET-роутам ЛК: состояние меняет только `/lk/epf/download` (выдаёт
одноразовый токен), и он отдаёт его в теле ответа, которое чужой origin
прочитать не может. Межсайтовые POST/PATCH/DELETE cookie по-прежнему не
получают. Защита, ради которой ставили `strict`, на месте.

### Что это значит для `session-probe.ts`

После выкладки `lax` ваш временный обход можно снимать — вход по ссылке
начнёт работать сам. Оговорка из вашего §1 про заблокированного тенанта
верна: `/lk/auth/session` отвечает `200`, а guard всё равно разворачивает.
Это не потерянная cookie, а отказ по статусу — так и задумано.

### Админка осталась на `Strict`

Сознательно: `/admin/*` закрыт IP-фильтром, входа по ссылке из письма и OAuth
у неё нет — межсайтовых переходов, ради которых ЛК переведён на `lax`, там
не бывает.

## 2. Почта: причина верная, но переключателей не хватало **в коде**

`SMTP_TLS_INSECURE=true` — правильный вывод, и в `auth.service.js` он
действительно уже поддержан. Но письма приглашений собирали **собственный**
транспорт — `user.service.js:257`:

```js
// было
const transporter = nodemailer.createTransport({ host, port, auth: { user, pass } });
await transporter.sendMail({ from: user, to, subject, text });
```

Эта копия:

| | общая версия | копия в user.service |
|---|---|---|
| `SMTP_TLS_INSECURE` | учитывает | **игнорирует** → та же ошибка сертификата |
| `SMTP_SKIP_AUTH` | учитывает | **игнорирует**, auth передаётся всегда |
| таймауты | 15 с | нет — запрос висит на мёртвом релее |
| отправитель | `EMAIL_FROM` | `SMTP_USER` мимо `EMAIL_FROM` |
| пустой `SMTP_USER` | письмо уходит | **молча не отправляет** |
| порт 465 | `secure: true` | не выставляет |

То есть после правки одного лишь `.env` подтверждение почты и сброс пароля
заработали бы, а приглашения продолжили бы падать — с той самой ошибкой
сертификата, которую «уже починили». Такое ищут долго.

Транспорт вынесен в **`services/lk-api/src/lib/mailer.js`**, оба места ходят
через него. Тесты на приглашения добавлены — в том числе на случай пустого
`SMTP_USER`.

### ⚠️ Главное про `.env` — правка нужна с вашей стороны, не с нашей

В нашем `.env` **обе строки уже стоят** и стояли до вашего разбора:

```
SMTP_SKIP_AUTH=true
SMTP_TLS_INSECURE=true
```

Раз в боевом контейнере ошибка сертификата всё ещё видна — значит на сервер
приехала **старая копия**: `.env` не в git, он попадает на прод из секрета
репозитория `ENV_FILE`. Обновить нужно именно секрет, кодом это не лечится.

Строки для секрета (плюс `NODE_ENV`, см. §3):

```bash
SMTP_SKIP_AUTH=true
SMTP_TLS_INSECURE=true
NODE_ENV=production
```

Про долгий вариант с сертификатом на `mail.corebridge.ru` — согласны, что для
локального релея избыточно. Если когда-нибудь релей переедет за пределы хоста,
`SMTP_TLS_INSECURE` придётся вернуть в `false`: в `.env.example` это записано.

## 3. `NODE_ENV=production` — сделано, но флаг Secure от него отвязан

Прогнали, как вы и просили. Итог: **2117 зелёных**, наборы одинаково проходят
и в обычном режиме, и с `NODE_ENV=production`.

Один тестовый набор при этом сначала падал — четыре теста
`server/tests/tenant_workspace.test.js` по таймауту. Причина не в режиме,
а в том, что backoff между retry сокращался условием `NODE_ENV === 'test'`:
с `production` он становился настоящим (5/15/30 с), и тесты не укладывались.
Переключили на `JEST_WORKER_ID` — признак прогона теперь берётся у самого jest
и от режима не зависит. Ваша осторожность тут оправдалась ровно.

Но сам вывод шире, чем «поставить production». `secure` был завязан на режим
сборки:

```js
secure: process.env.NODE_ENV === 'production',
```

Это неверная связь: «отдаём по HTTPS» и «режим сборки» — разные вещи, и одна
опечатка в `.env` молча снимает флаг с сессионной cookie. Что и произошло.
Теперь Secure стоит **по умолчанию** и снимается только явным
`COOKIE_SECURE=false` (для локальной отладки; `http://localhost` браузеры
и так считают безопасным контекстом). Так же поправлено в админке.

То есть `NODE_ENV=production` ставить стоит — но Secure он больше не решает,
и повторение этой истории уже невозможно.

## 4. Что проверить после выкладки

```bash
# 1. Письма уходят
docker logs corebridge-lk-api -f | grep email_
#    ожидаем "event":"email_sent"

# 2. Cookie: lax + Secure
curl -sSi -X POST https://corebridge.ru/lk/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"email":"...","password":"..."}' | grep -i set-cookie
#    lk_session=...; Path=/; HttpOnly; Secure; SameSite=Lax

# 3. Вход по ссылке из письма — руками, из почтового клиента
# 4. Приглашение в команду — письмо доходит и ссылка открывает кабинет
```

После пункта 2 можно удалять `lib/auth/session-probe.ts`.
