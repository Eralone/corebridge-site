## 1. S15 — удаление аккаунта

### 1.1. Почему ни один из трёх вариантов

Вы предложили: ослабить триггер / не хранить ПДн в журнале / завести привилегированную роль. И сами почти сформулировали ответ, когда написали:

> «Сам `uuid` уже никуда не ведёт: пользователя нет.»

Вот в этом и дело. **`lk_user:<uuid>` не содержит персональных данных** — это псевдоним. Замена его на `deleted_user:<uuid>` подменяла один uuid-идентификатор другим uuid-идентификатором: приватности это не добавляло ни на грамм, а ломалось об триггер и блокировало всю вторую фазу.

Поэтому обезличивание `actor` **убрано целиком**:

- 🔴 блокер снят — `purgeTenant` доходит до конца;
- триггер неизменяемости остался в полном объёме, журнал по-настоящему неподделываем (проверил: `UPDATE audit_log` по-прежнему отвергается);
- никакого чёрного хода и никакой привилегированной роли не появилось.

Это по сути ваш вариант 2 («не хранить ПДн в журнале»), но без миграции формата `actor` и без правки чтения — то есть тот же результат существенно дешевле.

### 1.2. Настоящая утечка была в `new_value` — она закрыта

Вы верно указали: `actor` обезличивался, а почта оставалась в теле записи. Нашёл **шесть** мест, писавших ПДн в журнал:

| Действие | Что писалось | Стало |
|---|---|---|
| `user_registered` (пароль) | `email`, `company_name` | `auth_provider`, `has_company`, `license_issued` |
| `user_registered` (Яндекс) | `email` | `auth_provider` |
| `email_verified` | `email` | — |
| `password_reset` | `email`, `ip` | `ip` (см. ниже) |
| `user_invited` | `email`, `role` | `role` |
| `invite_accepted` | `email` | `role` |

Email везде был **избыточен**: `entity_id` записи уже равен `user_id`, адрес читается из `platform.users`, пока пользователь существует. После удаления пользователя запись становится анонимной сама собой — ровно то, чего вы хотели добиться вариантом 2.

**Исторические записи вычищены** миграцией `027`: из `new_value` удаляются ключи `email`, `company_name`, `phone`, `user_email`, остальное содержимое сохраняется — смысл события («зарегистрировался», «принял приглашение») остаётся.

⚠️ **Миграция временно отключает триггер** — внутри своей транзакции, с включением обратно там же. Считаю это оправданным: разовая отревизованная операция по защите ПДн, выполняемая оператором; требование 152-ФЗ об удалении сильнее принципа неизменяемости журнала. Приложение таких прав не получает. Проверил после прогона: триггер включён, `UPDATE` отвергается.

**Про `ip` в `password_reset`.** Оставил сознательно, и хочу это проговорить: IP может считаться персональными данными, но здесь он — признак события безопасности, а не идентификатор клиента, и нужен при разборе компрометации. Если считаете, что его тоже надо убрать — скажите, правка на одну строку. Остальное проверил: телефона, ИНН и названия компании в журнале больше нет.

### 1.3. ⚠️ Сверх промта: cron писал `OK` даже при неудачах

Вы указали на это, и оказалось хуже: `purgeExpired()` возвращал только `results`, из которого вызывающему коду пришлось бы самому вычислять неудачи. Теперь возвращается явно:

```jsonc
{ "checked": 3, "purged": 2, "failed": 1,
  "failed_tenants": [{ "tenant_id": "…", "error": "…" }],
  "results": [ … ] }
```

`scripts/purge-deleted-tenants.js` выводит `failed_tenants` в лог и **завершается с кодом 1** при любой неудаче — cron и мониторинг это заметят. Именно так эта поломка и должна была всплыть месяц назад.

### 1.4. `confirm_company_name` у безымянного тенанта

Подтверждаю: если у тенанта нет названия, подтверждением служит **его `id`**, а не `null`. Это описано в коде и теперь в ответе; в `API_ENDPOINTS.md` допишите на своей стороне — файл ведёте вы.

## 2. S14 — переигрывание DLQ

### 2.1. Пути разведены по происхождению события

```
POST /admin/dlq/:id/reprocess

→ 200 { "success": true, "replay": "webhook" }      — входящее событие доставлено заново
→ 200 { "success": true, "replay": "tenant_init" }  — рабочее пространство переинициализировано
→ 409 { "error": "…", "code": "NOT_REPLAYABLE" }    — переигрывать нечем
→ 502                                                — переигрывание запускалось, внешний сервис отказал
→ 404                                                — записи нет
```

Классификация — по происхождению, а не по тексту:

| Событие | Способ |
|---|---|
| `workspace_init_failed` | `POST /internal/v1/tenants/:id/activate` — тот самый путь, который чинит 409 из S12 §5 |
| есть `_routing` / известен `event_type` | `POST /webhook/{tenant}/{type}`, как раньше |
| маршрута нет | `409 NOT_REPLAYABLE` |

На `/{tenant}/unknown` сервис больше не ходит **ни при каких данных** — есть отдельный тест.

**`409` вместо `502` — по вашей же формулировке:** 502 читается как «сломался n8n», и админ идёт чинить здоровый сервис. Теперь код машинный (`NOT_REPLAYABLE`), так что временный список в `QueuesBody.tsx` можно снять — сайт узнаёт непереигрываемое событие из ответа.

### 2.2. `reprocess-all` больше не считает их сбоем

```jsonc
{ "reprocessed_count": 5, "failed_ids": [], "skipped_ids": ["…", "…"] }
```

Непереигрываемые уходят в `skipped_ids`. Раньше они попадали в `failed_ids` при каждом запуске и выглядели как повторяющийся сбой — админ раз за разом «чинил» несуществующую проблему.

### 2.3. ⚠️ Сверх промта: удаление из очереди тоже было сломано

Вы написали, что «листинг и удаление работают». Листинг — да, удаление — нет:

```js
UPDATE platform.dead_letter_queue SET status = 'deleted', updated_at = NOW() ...
```

**Ни колонки `status`, ни `updated_at` в таблице не существует** — это тот же класс дефекта, что четыре из S13. Проверил на живой БД:

```
ERROR: column "status" of relation "dead_letter_queue" does not exist
```

То же было в `reprocessEvent` — он писал `SET status = 'reprocessed'` после успешной отправки.

Мягкое удаление здесь и не нужно: очередь по смыслу содержит только неразобранное. Теперь разрешённая запись **удаляется**, а след остаётся в `audit_log` (`admin_dlq_reprocessed` / `admin_dlq_deleted` с `tenant_id` и `event_type` — чтобы после удаления можно было восстановить картину).

Заодно убран фильтр `?status=` из `listDLQ` — фильтровать было не по чему.

## 3. Реальные .epf вместо заглушек

### 3.1. ⚠️ Сверх промта: выкладка упиралась в лимит nginx

Проверил путь публикации живым запросом на прод — и он не прошёл:

```
POST https://api.corebridge.ru/api/v1/epf/publish  →  413 Payload Too Large
```

Отвечает **nginx**, до приложения запрос не доходит. Обработки весят
1.17–1.30 МБ, а на хосте действует умолчание `client_max_body_size` (1 МБ):
в репозитории лимит задан в `nginx/nginx.conf`, но деплой этот файл не
применяет — он лишь правит `include` в системном `nginx.conf` Ubuntu.

Это значит, что **и автовыкладка, которую я настроил, упала бы точно так же**.
Хорошо, что вы попросили перепроверить: без этого CI молча падал бы на каждой
сборке.

Исправлено в `nginx/sites-enabled/api.corebridge.ru.conf` — отдельный `location`
для `/api/v1/epf/` **до** общего `/api/v1/`:

```nginx
location /api/v1/epf/ {
    client_max_body_size 60m;      # предел приложения (multer) — 50 МБ
    proxy_request_buffering off;   # не копим файл целиком перед отправкой
    proxy_read_timeout 300s;
    ...
}
```

`deploy.sh` симлинкует конфиги и делает `nginx -s reload`, так что правка
применится сама на ближайшем деплое. **До этого выложить .epf нельзя** — ни
автоматически, ни вручную через API.

### 3.2. Автоматическая выкладка — основной путь

Серверная часть автоматики **уже существовала**: `POST /api/v1/epf/publish`
(bridge) принимает файл multipart-ом, сохраняет на диск, регистрирует версию
и активирует её; защищён `Bearer ADMIN_API_KEY`. Не хватало того, кто его вызовет.

Написан воркфлоу `corebridge-epf/.github/workflows/publish-epf.yml`:

1. Срабатывает на push в `main`, если изменились `dist/unified_*.epf`.
2. Считает версию сам: `MAJOR.MINOR` из файла `VERSION`, `PATCH` — число
   коммитов, менявших обработки после последней правки `VERSION`. Схема
   детерминированная и монотонная: одна правка = +1 к patch, изменение
   `VERSION` (1.0 → 1.1) обнуляет счётчик. Обратной записи в репозиторий нет —
   из-за неё CI зацикливался бы сам на себе.
3. Публикует **только изменившиеся** конфигурации: пересобрали один `ut11` —
   трём остальным клиентам обновление не прилетит.
4. Отказывается публиковать файл меньше 50 КБ — на прод не уедет заглушка.
5. Ставит тег и прикладывает сборки к Release для истории и отката.

Первая выкладка после коммита `VERSION` даст `v1.0.0` (проверил расчёт на вашей
реальной истории), дальше `v1.0.1` и так далее.

**Что нужно сделать один раз в `corebridge-epf`:**

1. Секрет: Settings → Secrets and variables → Actions → `COREBRIDGE_PUBLISH_TOKEN`,
   значение — то же, что `ADMIN_API_KEY` на сервере.
2. Закоммитить два файла: `VERSION` (содержит `1.0`) и
   `.github/workflows/publish-epf.yml`. Я их создал, но это отдельный
   репозиторий — коммит там за вами.

Безопасная проверка: Actions → Publish EPF → Run workflow → `dry_run: true`.

### 3.3. Запасной путь — прямой вызов API

Скрипт `scripts/epf/publish_epf_local.js` пригоден только для запуска из копии
репозитория (нужны `node_modules` и доступ к БД). **Внутрь контейнеров он не
попадает**: `admin` собирается с `context=./services/admin` и копирует лишь
`src/`, `bridge` копирует `scripts/epf-tests/`, но не `scripts/epf/`.

Поэтому для ручной выкладки надёжнее тот же эндпоинт, что использует CI —
он работает откуда угодно и ничего не требует, кроме `curl`:

```bash
for c in ut11 unf ka bp; do
  curl -sS -X POST https://api.corebridge.ru/api/v1/epf/publish \
    -H "Authorization: Bearer $ADMIN_API_KEY" \
    -F "file=@dist/unified_${c}.epf" \
    -F "config=${c}" \
    -F "version=v1.0.0"
done
```

Формат версии общий с CI (`v1.0.0`) — иначе на диске появились бы два разных
каталога для одной версии.

### 3.4. Сборки проверены

Прогнал весь путь на локальной БД — файлы читаются, пишутся байт в байт
(сверил хэши источника и результата), версии регистрируются и активируются:

| Конфигурация | Размер | sha256 |
|---|---|---|
| `ut11` | 1 361 372 б (1.30 МБ) | `ad5f9eff3bf221e5…` |
| `unf` | 1 343 502 б (1.28 МБ) | `a158d4b851a7bbc9…` |
| `ka` | 1 349 596 б (1.29 МБ) | `7cd2dc320e89e0d4…` |
| `bp` | 1 226 312 б (1.17 МБ) | `b08ec00db270dc6e…` |

Защита от повторения истории с заглушками: и скрипт, и воркфлоу отказываются
публиковать файл меньше 50 КБ. Проверил на специально созданных 75-байтовых
файлах — публикация прерывается до первой записи, в БД ничего не попадает.

### 3.5. ⚠️ Убран сломанный воркфлоу

В `corebridge-server` лежал `.github/workflows/epf-release.yml`, написанный для
**другого** репозитория: он вызывает `scripts/build_epf.sh`, которого здесь нет
(в `corebridge-epf` сборщик называется `build_epf.py`). При этом он был подписан
на `push: tags: v*` в **этом** репозитории — то есть любой тег `v*` на сервере
запускал бы его и валил сборку. Удалён; рабочая версия живёт в `corebridge-epf`.

### 3.6. Как убедиться, что заработало

После деплоя (когда применится правка nginx):

```bash
# 1. Публикация проходит
curl -sS -o /dev/null -w '%{http_code}\n' -X POST \
  https://api.corebridge.ru/api/v1/epf/publish \
  -H "Authorization: Bearer $ADMIN_API_KEY" \
  -F "file=@dist/unified_ut11.epf" -F "config=ut11" -F "version=v1.0.0"   # 200, не 413

# 2. Сквозной путь выдачи из S11
curl -s -H "Cookie: lk_session=<сессия>" 'https://corebridge.ru/lk/epf/download?config=ut11'
curl -s -o /tmp/x.epf -w '%{http_code}\n' 'https://corebridge.ru/cdn/epf/download?token=<token>'  # 200
sha256sum /tmp/x.epf   # должен совпасть с таблицей в §3.4
```

Заглушки версии `0.0.1` после этого можно снять с активации — они останутся в истории.

## 4. Что нужно сделать при деплое

1. **Применить миграцию `027`** (зачистка ПДн из журнала). Необратима по смыслу: удалённые персональные данные не восстанавливаются, и не должны.
2. **Дождаться применения правки nginx** — она едет вместе с деплоем (`deploy.sh` симлинкует конфиги и делает `nginx -s reload`). Проверить: публикация .epf возвращает 200, а не 413 (§3.6).
3. **Выложить .epf** — автоматически из `corebridge-epf` (§3.2) или вручную (§3.3).
4. **Поправить ночной cron.** Прежняя команда была неверна: `scripts/purge-deleted-tenants.js` в контейнер не попадает (образ `admin` копирует только `src/`). Рабочий вариант — скрипт, который ездит внутри образа:

```
30 3 * * * root docker exec corebridge-admin node src/scripts/purge_expired.js
```

Проверить вхолостую: `docker exec corebridge-admin node src/scripts/purge_expired.js --dry-run`
