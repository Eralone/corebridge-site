## 1. S10 — учёт операций

### 1.1. Корень был глубже, чем в промте

Прежде чем чинить `_getN8nExecLimit`, проверил, откуда лимит **должен** был браться. Оказалось, «правильный» источник сам сломан:

```js
// server/services/n8n/execution_limit.js
SELECT (limits->>'n8n_executions_month')::INTEGER FROM platform.licenses
```

Колонки `limits` в `platform.licenses` **нет вовсе** — тот же класс дефекта, что все четыре в S13:

```
ERROR: column "limits" does not exist
```

То есть учёт держался исключительно на захардкоженном `1000`, а механизм, который должен был подставлять настоящий лимит, не работал никогда.

**Что сделано.** Миграция `026` добавляет в `platform.licenses` колонки `limits` и `features` — снимок тарифа на момент выдачи, с бэкфиллом по каталогу для существующих лицензий. `issueLicense` теперь их записывает. Любой сервис берёт лимит обычным `SELECT`, без кросс-сервисных импортов и без дублирования каталога тарифов.

### 1.2. Лимит соответствует тарифу с первого события

`event-dispatcher` читает лимиты из активной лицензии. Фолбэк — не `1000`, а самый скромный тариф (500): занизить безопаснее, чем раздать лишнее.

**Смена тарифа посреди месяца** тоже закрыта: `issueLicense` обновляет `limit_value` в строке текущего периода. Иначе оплативший «Профессионала» упирался бы в лимит «Пробного» до первого числа.

### 1.3. `limit` больше не ноль до первого запуска

```jsonc
GET /lk/dashboard → {
  "n8n_usage":        { "used": 0, "limit": 20000,  "is_limit_hit": false, "period": "2026-07" },
  "operations_usage": { "used": 0, "limit": 100000, "is_limit_hit": false, "period": "2026-07" }
}
```

Нулём остаётся только `used`; `limit` всегда отражает тариф. `period` проставляется даже когда строки счётчика ещё нет.

**Обход на вашей стороне можно снимать** — `n8n_usage.limit` теперь верен. Но он безвреден, спешки нет.

### 1.4. Мягкий лимит — и почему именно так

Реализовано: считаем, показываем, уведомляем на 80 % и 100 %. Обработку **не блокируем**.

Причина: `is_limit_hit` в системе уже есть, но ни одна проверка на него не смотрит — то есть жёсткого лимита никогда и не было. Включить блокировку означало бы в один момент остановить обмен у всех, кто перерос тариф, без предупреждения и без вашего продуктового решения. Это ломающее изменение, его нельзя вводить попутной правкой.

Если жёсткий лимит нужен — присылайте отдельный промт: что блокировать (только новые события или и уже принятые), что отвечать `.epf`, и нужен ли grace-период.

### 1.5. Уведомления

Пороги 80 % и 100 % включены в существующее `limit_exceeded` (F17). Один раз на порог за период — дедупликация на уровне БД. Отдельной настройки не требуется: канал и матрица у пользователя уже есть с S4.

## 2. S11 — скачивание .epf

Диагноз в промте верный. Сделаны **оба** варианта, как вы и предлагали.

**Вариант 2** — явные параметры в `epf_download.service.js`. Пароль подставляется, только если его нет в самом URL: иначе корректные учётные данные затёрлись бы пустым значением.

**Вариант 1** — `REDIS_URL=redis://:${REDIS_PASSWORD}@redis:6379/0` в `.env`.

### ⚠️ Сверх промта: та же переменная ломала ещё два сервиса

`REDIS_URL` без пароля берут не только `epf_download`, но и:

- `services/bridge/src/index.js` — кеш JWT, rate-limit,
- `services/license-service/src/index.js` — кеш лицензий.

Оба создают клиент без `password`, то есть у них Redis тоже отвечал `NOAUTH`. Там graceful degradation, поэтому отказ не был виден: сервисы работали, просто без кеша — с лишней нагрузкой на БД и без сквозного rate-limit. Обоим добавлена та же защита.

Проверьте после деплоя, что в логах `corebridge-bridge` и `corebridge-license-service` пропали `NOAUTH`.

### 3.3. ⚠️ Семантика `required_integrations` изменена — прошу перечитать

Вы верно определили, что сверка шла не по тому словарю. Но при исправлении вскрылось второе: буквальное «нужны ВСЕ перечисленные» бессмысленно. Шаблон «Заказы с маркетплейсов» поддерживает Ozon, WB и ЯМ — требовать все три сразу значит не включить его никому.

Раз сайт даёт выбрать интеграцию в карточке, проверяется именно она:

```
POST /lk/workflows/activate { template_id, integration_id }

→ 404 INTEGRATION_NOT_FOUND            — такой интеграции у тенанта нет
→ 409 INTEGRATION_TYPE_NOT_SUPPORTED   — тип не подходит шаблону
   { "error": "INTEGRATION_TYPE_NOT_SUPPORTED",
     "adapter_type": "wb",
     "supported": ["ozon"] }
→ 200                                   — включено
```

Пустой `required_integrations` = подходит любая интеграция.

**Что это значит для вас:** `MISSING_REQUIRED_INTEGRATION` больше не возвращается. Читайте `required_integrations` как «поддерживаемые типы» — по нему же фильтруйте выпадающий список интеграций в карточке. `supported` в ответе позволяет объяснить пользователю, что именно подключить.

### 3.4. История запусков

Баг приоритета операторов исправлен — скобки на месте. `error`, `crashed`, `canceled` передаются как есть.

`startedAt` → **`started_at`**. Меняйте у себя после деплоя.

`?limit=` теперь учитывается: дефолт 50, потолок 200.

### 3.5. Инициализация n8n: 409

Причину нашёл. Инициализацию запускают **два независимых пути**: `issueLicense` дёргает `/internal/v1/tenants/:id/activate` через `setImmediate`, и bridge делает ленивую инициализацию при первом запросе тенанта (фолбэк F6.1). Оба вызывают `listTags` (пусто), оба идут создавать тег. Один выигрывает, второй получает `409` — и, как вы и предположили, трактовал конфликт как отказ: три ретрая, DLQ, `n8n_initialized = false`.

Теперь `409` от `createTag` означает «тег уже создан»: сервис перечитывает список, берёт существующий тег и завершает инициализацию успешно. Не-409 ошибки ретраятся как прежде — есть тесты на оба случая и на «409, но тега всё равно нет» (это уже другая проблема, ретрай отрабатывает).

**Про видимость:** согласен, что узнавать о неработающем клиенте из DLQ неправильно. Плитка `n8n` в `/admin/health` уже есть (S9). Отдельный алерт «у тенанта не инициализирован workspace» логично добавить в диспетчер уведомлений — если нужно, пришлите промт, там нужно решить, кому это уведомление адресовано (администратору платформы, не клиенту).

**Сверх промта — те же два запроса в `dlq_mgmt.service.js`:**

```js
"SELECT * FROM platform.dead_letter_queue WHERE id = $1 AND status = 'pending'"        // reprocessEvent
"SELECT id FROM platform.dead_letter_queue WHERE tenant_id = $1 AND status = 'pending'" // reprocessAll
```

Вы отметили, что `dlq_mgmt` «работает» — работает листинг, а вот **переобработка падала так же**. Обе кнопки («Переобработать» и «Переобработать все») возвращали бы 500. Исправлено.

**Про историю токенов:** `issued_by_admin` вычисляется из `audit_log` — по вашей же наводке, что там точнее. Ищется запись `admin_token_issued` / `admin_set_plan` / `admin_trial_granted` с `actor LIKE 'admin:%'` в окне ±1 минута от выдачи лицензии. Полный JWT в ответ не попадает даже администратору — только первые 12 символов: это действующий доступ.

**Про схему `epf_versions`:** у меня локально `is_public` и `tenant_id` **есть**, у вас на проде нет. То есть базы разошлись. Правка от этого не зависит — колонки просто не выбираются, запрос работает в обеих схемах. Но расхождение стоит проверить: `node db/migrate.js status` на проде.

### 4.3. Дубль DLQ удалён

`marketplace.dead_letter_queue` была пуста, и ни один `INSERT` в неё не ведёт — все три источника (`event-dispatcher`, `n8n-dispatcher`, `tenant_workspace`) пишут в `platform.dead_letter_queue`. Миграция `025` её удаляет, **но только если она пуста**: если на проде окажутся строки, миграция их не тронет и напечатает предупреждение. Молча терять события из мёртвой очереди нельзя.

### 4.4. Вход без TOTP

Сделаны **оба** варианта — чтобы текущий сайт с заглушкой не сломался в момент деплоя:

- при `totp_enabled = false` сессия выдаётся **сразу на шаге 1**, cookie ставится там же;
- `step_token` продолжает возвращаться, а `/totp/verify` больше не требует непустой `totp_code`.

Переходите на одношаговый вход, когда вам удобно.

```
POST /admin/auth/login → 200 { "requires_totp": false, "step_token": "…" }
                         + Set-Cookie: admin_session_id
```

`session_id` в теле не отдаётся — только в httpOnly-cookie.

### 4.5. Про TOTP — поддерживаю

Вопрос к Дмитрию, но со стороны сервера подтверждаю: панель меняет тарифы, блокирует тенантов и **запускает удаление аккаунтов** (S8). Защита паролем и IP-whitelist для этого мало. TOTP реализован полностью, включается через `/admin/auth/totp/setup` — стоит включить до передачи панели в работу.
