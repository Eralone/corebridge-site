## 1. Архитектурный принцип

```
1С (клиент)                      CoreBridge Server                Внешний сервис
┌─────────────────────┐           ┌───────────────────┐           ┌──────────────┐
│  unified_{cfg}.epf  │  HTTPS    │  api.corebridge   │  REST /   │ Ozon / WB /  │
│                     │ ────────▶ │  .ru              │  webhook  │ CRM / ЮKassa │
│  CommonModules (22) │ ◀──────── │  Node.js +        │ ◀──────── │ СДЭК / ...   │
│  Polling / Hooks    │  polling  │  PostgreSQL +      │           └──────────────┘
└─────────────────────┘           │  Redis + n8n      │
                                  └───────────────────┘
```

**Ключевые ограничения .epf:**
- Только исходящие HTTPS-запросы — порты не открывает, входящих нет
- Прямых вызовов API маркетплейсов из .epf нет — только к `api.corebridge.ru`
- Данные клиента не покидают его сеть (только JSON-события на сервер платформы)
- Каждый EPF-файл собирается в 4 вариантах: `ut11`, `unf`, `ka`, `bp`

**Четыре EPF-файла:**

| Конфигурация 1С | Config ID | EPF-файл |
|---|---|---|
| УТ 11 (Управление торговлей) | `ut11` | `unified_ut11.epf` |
| УНФ (Управление нашей фирмой) | `unf` | `unified_unf.epf` |
| КА 2 / ERP | `ka` | `unified_ka.epf` |
| БП 3.0 (Бухгалтерия предприятия) | `bp` | `unified_bp.epf` |

## 2. Глобальные соглашения

### HTTP-заголовки (все запросы)

```
Authorization: Bearer {JWT}
X-EPF-Version: {текущая_версия}
Content-Type: application/json
```

### Базовые эндпоинты (используются всеми механиками)

| Эндпоинт | Метод | Назначение |
|---|---|---|
| `/api/v1/license/check` | GET | Проверка JWT + `enabled_modules` при старте |
| `/api/v1/health` | GET | Проверка соединения (Мастер подключения) |
| `/api/v1/config/validate` | POST | Валидация API-ключа внешнего сервиса через сервер |
| `/api/v1/events` | GET | Polling входящих событий (polling-механики) |
| `/api/v1/events/{id}/ack` | POST | ACK подтверждения обработки события |
| `/api/v1/epf/{config}/version` | GET | Проверка актуальности версии .epf (без JWT) |

### ACK-протокол

```bsl
// Отправлять ACK только при успешной записи документа в 1С.
// При ошибке — НЕ отправлять ACK, событие вернётся при следующем polling.
// Тело ACK:
// { "status": "success" | "failed" | "duplicate", "doc_ref": "UUID документа 1С" }
```

### Коды ответов и поведение

| HTTP-код | Действие |
|---|---|
| `402` | Показать форму продления лицензии, остановить polling |
| `429` | Exponential backoff, не роняет другие интеграции |
| `5xx` | Retry с backoff, запись в ЖурналСобытий |

### BSL-соглашения по именованию

```
Процедуры/функции:  КаждоеСловоСБольшойБуквы()   // ПолучитьЗаказы, ОтправитьОстатки
Переменные:         каждоеСловоСБольшойБуквы       // новыйЗаказ, суммаОплаты
Константы:          ПРОПИСНЫМИ_БУКВАМИ              // ВЕРСИЯ_API, URL_СЕРВЕРА
CommonModules:      Модуль + назначение             // МодульЗаказов, МодульОплаты
```

### IF-блоки кодогенерации (из `config_matrix.json` → секция `Поведение`)

```
{{IF НужнаОрганизация}}...{{ENDIF НужнаОрганизация}}     — только ka
{{IF ЕстьПартнёр}}...{{ENDIF ЕстьПартнёр}}               — только ka
{{IF ЕстьСклад}}...{{ENDIF ЕстьСклад}}                   — ut11, unf, ka (не bp)
{{IF РезервыПоддерживаются}}...{{ENDIF}}                  — ut11, unf, ka (не bp)
{{IF ОрдернаяСхемаFBM}}...{{ENDIF}}                       — только ut11
{{IFNOT ЕстьСклад}}...{{ENDIFNOT ЕстьСклад}}             — только bp (заглушка)
```

### Механика 1 — Заказы FBS/FBO (`marketplace_orders`)

**BSL-модуль:** `МодульЗаказов` · **Задание:** `ОсновнойЦикл` (15 сек) · **Шаблон:** `МодульЗаказов_template.bsl`

**Что происходит:**
1. `ОсновнойЦикл()` делает `GET /api/v1/events?adapter=ozon&type=order_*`
2. Для каждого события вызывает `ОбработатьСобытиеЗаказа(событие)`
3. Создаёт документ-заказ в 1С, проводит его
4. При успехе — `POST /api/v1/events/{id}/ack` со статусом `success` и `doc_ref`
5. Внутри `ОбработатьСобытиеЗаказа()` вызывает хуки маркировки (мех. 9) и ГТД (мех. 10)

**Объекты 1С (документы):**

| Конфигурация | Документ заказа | Ключевые реквизиты |
|---|---|---|
| УТ 11 | `Документы.ЗаказПокупателя` | Контрагент, Склад, Договор, ТЧ Товары |
| УНФ | `Документы.ЗаказКлиента` | Контрагент, Склад, Договор, ТЧ Товары |
| КА 2/ERP | `Документы.ЗаказКлиента` | Организация (**обязательна**), Партнёр, Контрагент, Склад, Договор |
| БП 3.0 | `Документы.СчётНаОплату` | Контрагент, Договор, ТЧ Товары (нет Склада) |

**Справочники (читаются при создании документа):**

| Справочник | УТ 11 | УНФ | КА | БП |
|---|---|---|---|---|
| Номенклатура | `Справочники.Номенклатура` | ✅ | ✅ | ✅ |
| Контрагенты | `Справочники.Контрагенты` | ✅ | ✅ | ✅ |
| Склады | `Справочники.Склады` | ✅ | ✅ | — |
| Договоры | `Справочники.ДоговорыКонтрагентов` | ✅ | ✅ | ✅ |
| Организации | `Справочники.Организации` | — | ✅ (обяз.) | ✅ |
| Партнёры | — | — | `Справочники.Партнёры` | — |
| ТипыЦен | `Справочники.ТипыЦенНоменклатуры` | `Справочники.ТипыЦен` | `Справочники.ВидыЦен` | `Справочники.ТипыЦенНоменклатуры` |

**ТЧ Товары (одинакова для всех конфигураций):**

| Колонка BSL | Имя ТЧ | Поля |
|---|---|---|
| `ИмяТЧ` | `Товары` | `Цена`, `Сумма`, `ЕдиницаИзмерения` |

**API платформы:**

```http
GET /api/v1/events?adapter=ozon&type=order_new,order_confirmed,order_cancelled
Authorization: Bearer {JWT}
```

**Структура события (сервер → .epf):**

```json
{
  "event_id": "uuid",
  "event_type": "order_new",
  "adapter": "ozon",
  "integration_id": "MP_001",
  "data": {
    "order_id": "12345678",
    "order_number": "54321",
    "status": "awaiting_packaging",
    "shipment_method": "FBS",
    "items": [
      {
        "sku": "ART-001",
        "name": "Товар А",
        "qty": 2,
        "price": 1500.00,
        "vat": "vat20"
      }
    ],
    "customer": {
      "name": "Иван Иванов",
      "phone": "+79001234567",
      "address": "Москва, ул. Ленина, 1"
    },
    "warehouse_id": "WH-01",
    "created_at": "2026-04-26T10:00:00Z"
  }
}
```

**ACK (payload, .epf → сервер):**

```json
{
  "status": "success",
  "doc_ref": "cf8b7a2e-0001-4001-8001-000000000001"
}
```

**Events:** `order_new` · `order_confirmed` · `order_cancelled` · `order_status_changed`

**Поддержка маркетплейсов:** Ozon ✅ · WB ✅ · ЯМ ✅

**IF-блоки шаблона:**
- `{{IF НужнаОрганизация}}` — добавляет проверку и заполнение `Организация` (ka)
- `{{IF ЕстьПартнёр}}` — добавляет поиск/создание `Партнёра` и привязку (ka)
- `{{IF ЕстьСклад}}` — заполняет реквизит `Склад` в документе (ut11/unf/ka)
- `{{IFNOT ЕстьСклад}}` — пропускает складские реквизиты тихо (bp)

### Механика 2 — Отгрузка (`marketplace_shipment`)

**BSL-модуль:** `МодульОтгрузки` · **Задание:** `ОсновнойЦикл` · **Шаблон:** `МодульОтгрузки_template.bsl`

**Что происходит:**
1. Подписка на событие проведения документа-заказа в 1С
2. `ОбработатьОтгрузку()` создаёт документ отгрузки на основании заказа
3. Проводит документ отгрузки
4. Сообщает серверу, что отгрузка создана (ACK-событие)
5. Вызывает хук доставки (мех. 17) если настроен

**Объекты 1С (документы):**

| Конфигурация | Документ отгрузки | Триггер (ПодпискаНаСобытие) |
|---|---|---|
| УТ 11 | `Документы.РасходнаяНакладная` | `ПослеЗаписи(ЗаказПокупателя, ПриПроведении)` |
| УНФ | `Документы.РасходнаяНакладная` | `ПослеЗаписи(ЗаказКлиента, ПриПроведении)` |
| КА 2/ERP | `Документы.РеализацияТоваровУслуг` | `ПослеЗаписи(ЗаказКлиента)` + режим «Раз в день» |
| БП 3.0 | `Документы.РеализацияТоваровУслуг` | `ПослеЗаписи(СчётНаОплату, ПриПроведении)` |

**API платформы:**

```http
GET /api/v1/events?adapter=ozon&type=shipment_ready
POST /api/v1/events/{id}/ack
```

**Поддержка:** Ozon ✅ · WB ✅ · ЯМ ✅

**IF-блоки:** `{{IF НужнаОрганизация}}` · `{{IF ЕстьСклад}}`

## 15. Система кодогенерации BSL

### Три файла системы

| Файл | Роль |
|---|---|
| `src/config_matrix.json` | Источник истины: все объекты 1С по всем конфигурациям |
| `src/templates/{mechanic}_template.bsl` | Шаблон BSL с плейсхолдерами `{{Ключ}}` / `{{IF ...}}` |
| `scripts/build_config.py` → `TEMPLATE_MAP` | Реестр шаблонов и выходных путей |

### Синтаксис шаблонов

```
{{ДокументЗаказ}}                             → подстановка из config_matrix.json
{{IF НужнаОрганизация}}...{{ENDIF}}           → блок только для ka
{{IFNOT ЕстьСклад}}...{{ENDIFNOT}}           → блок только для bp
```

### Механики вне системы кодогенерации (единые EPF)

Эти механики не проходят через `build_config.py` — у них нет конфигурационных вариантов:

| Механика | Путь | Файл модуля |
|---|---|---|
| 10 — ГТД | `src/epf/marketplace_gtd/` | `GTDModule.bsl` |
| 12 — Этикетки | `src/epf/marketplace_labels/` | `ObjectModule.bsl` |
| 20 — Уведомления | `src/epf/notifications/` | `МодульУведомлений.bsl` |
| 22 — Иное | `src/epf/custom/` | `МодульИное.bsl` |

### Чеклист добавления новой механики

1. Создать `src/templates/{mechanic}_template.bsl` с плейсхолдерами
2. Добавить строку в `TEMPLATE_MAP` в `scripts/build_config.py`
3. Запустить `python scripts/build_config.py --dry-run`, проверить `UNRESOLVED`
4. Запустить `python scripts/build_config.py`, сгенерируются файлы для всех 4 конфигураций
5. Собрать EPF: `python3 scripts/build_epf.py <mechanic_name>` — все 4 конфигурации должны появиться в `dist/`
6. Обновить `CLAUDE.md` разделы 3.5, 5, 6, 7, 8, 9
7. Обновить `README.md` — таблицу механик
